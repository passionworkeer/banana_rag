# 后续方案设计问题清单

调研日期：2026-05-29

这份清单用于把调研收敛成可执行架构方案。不是所有问题都要一次回答，但标为 P0 的问题会直接影响技术路线。

## 1. P0：必须先确认

### 1.1 部署和数据边界

1. 数据是否允许出企业内网？
2. 是否允许调用外部云模型 API？
3. 是否必须全私有化部署？
4. 是否有等保、金融、政企、医疗、审计、跨境数据等合规要求？
5. 日志、问题、答案、引用片段是否也算敏感数据？

影响：

- 如果必须全私有化，优先评估 vLLM/Xinference/Ollama/TEI + 私有向量库/搜索库。
- 如果允许混合云，可以把低敏问答接云模型，高敏文档走私有模型。

### 1.2 文档来源

1. 第一批最重要的文档来源是什么？
2. 是员工手动上传为主，还是从 SharePoint/飞书/Confluence/OA/网盘自动同步为主？
3. 是否需要保留源系统权限？
4. 文档删除、移动、改名、撤权是否必须实时同步？
5. 有没有大量扫描 PDF、图片、PPT、Excel 表格？

影响：

- 如果源系统权限复杂，必须优先设计 ACL 同步。
- 如果扫描件多，OCR/版式解析要进入第一期。

### 1.3 权限模型

1. 只需要部门隔离，还是需要项目/岗位/密级/临时授权？
2. 是否存在跨部门项目组？
3. 是否有“法务、财务、人事、战略”等高敏部门？
4. 是否允许部门 Agent 代表用户跨部门询问？
5. 跨部门知识访问是否需要审批？

影响：

- 只有部门隔离：RBAC + metadata filter 足够起步。
- 有复杂项目和继承权限：需要 ABAC/ReBAC，考虑 OpenFGA/SpiceDB/OPA/Cerbos。

### 1.4 用户规模和数据规模

1. 预计第一期多少员工使用？
2. 预计文档量多少：1 万、10 万、100 万还是更多？
3. 文档平均大小和总容量大概多少？
4. 每天新增/更新文档多少？
5. 预计 QPS、并发、P95 延迟目标是多少？

影响：

- 中小规模可用 PostgreSQL + pgvector 快速起步。
- 大规模需要 Qdrant/Milvus/Weaviate + OpenSearch。
- 高并发需要模型服务、embedding、rerank 独立扩缩容。

## 2. P1：影响架构质量

### 2.1 业务场景

1. 员工主要是“搜索文档”，还是“问答总结”，还是“让 Agent 帮忙办事”？
2. 是否需要对答案进行审批或人工确认？
3. 是否需要生成报告、制度解读、合同审查、故障排查方案？
4. 是否需要接入企业微信、飞书、钉钉或门户？
5. 是否需要开放 API 给内部系统调用？

### 2.2 答案可信度

1. 答案是否必须带引用？
2. 是否允许模型在没有资料时根据常识回答？
3. 是否需要显示置信度？
4. 是否需要把引用定位到页码、段落、表格单元格或 PPT 页？
5. 是否需要返回原文片段供员工核对？

建议：

- 企业知识库默认必须带引用。
- 无引用时不应回答确定结论。
- 高风险领域需要“仅基于资料回答”。

### 2.3 文档治理

1. 谁能上传文档？
2. 上传后是否需要审核？
3. 谁负责文档过期、下架、版本合并？
4. 是否需要按部门配置知识管理员？
5. 是否需要自动发现过期制度和重复文档？

### 2.4 Agent 协作

1. 第一批 Agent 是哪些：HR、法务、研发、销售、客服、财务？
2. Agent 之间通信只是问答，还是能发起流程？
3. Agent 是否能调用 OA、工单、CRM、代码仓库等工具？
4. 哪些操作必须人工确认？
5. Agent 的调用链是否要对终端用户可见？

建议：

- 第一版 Agent 只做受控问答和总结。
- 工具写操作必须后置到第二阶段，并加审批。

## 3. P2：影响选型和成本

### 3.1 技术栈偏好

1. 团队主要技术栈是 Java、Python、Go、Node.js 还是 .NET？
2. 是否已有 Kubernetes？
3. 是否已有 OpenSearch/Elasticsearch？
4. 是否已有 PostgreSQL、Redis、Kafka、MinIO/S3？
5. 是否已有数据中台、DataHub/OpenMetadata/Atlas？

### 3.2 模型偏好

1. 是否偏向 Qwen、DeepSeek、Llama、GLM、Kimi、OpenAI、Claude、Gemini？
2. 是否需要中文优先？
3. 是否需要中英混合？
4. 是否需要本地 embedding 和 reranker？
5. 是否有 GPU 资源？

### 3.3 成本边界

1. 是否更关心初期上线速度，还是长期可控成本？
2. 是否能接受云 API 按量费用？
3. 是否已有 GPU 服务器或预算？
4. 是否允许按部门限制使用额度？
5. 是否需要成本归因到部门？

## 4. 建议的默认答案

如果当前还没有明确答案，可以先按以下假设推进架构设计：

- 部署：核心平台私有化，模型网关可插拔。
- 文档来源：人工上传 + 一个核心文档系统。
- 权限：部门/空间 RBAC 起步，元数据预留项目、密级、ACL。
- 检索：OpenSearch + Qdrant，混合检索 + rerank。
- 解析：Docling + MinerU/PaddleOCR + Tika 兜底。
- 编排：LlamaIndex 做 RAG，LangGraph 做 Agent。
- Agent：第一期只做部门问答 Agent，不做自动写操作。
- 安全：检索前权限过滤，答案必须引用，审计全链路记录。
- 评估：每个试点部门 30-50 个问题，包含权限负例。

## 5. 我建议你优先回答的 6 个问题

1. 你们是否必须全私有化，还是可以用云模型？
2. 第一批要接入的文档来源是哪几个？
3. 权限只按部门隔离，还是要细到项目、岗位、密级、个人授权？
4. 文档规模大概是多少：文档数、总容量、每日新增量？
5. 第一批典型场景是员工问答，还是 Agent 帮员工执行流程？
6. 是否已有 SSO/AD/LDAP、OpenSearch、PostgreSQL、对象存储、Kubernetes 等基础设施？
