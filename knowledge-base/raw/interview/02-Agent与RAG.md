# 02 Agent 与 RAG

## 1. 什么是 RAG？标准 RAG 有什么问题？它和传统“检索 + 模型生成”有什么不同？

核心回答：

> RAG 是 Retrieval-Augmented Generation，先从外部知识源检索相关内容，再把检索结果交给大模型生成答案。它和传统“先搜再答”最大的区别在于，RAG 把检索结果以模型可消费的上下文形式注入生成过程，而不是只返回搜索结果列表。

标准 RAG 的问题：

- **切片不合理**：切太碎会丢上下文，切太大又会稀释召回。
- **召回不准**：检索到的内容可能语义接近但不真正相关。
- **Top-K 噪声**：检索结果多了以后，无关内容会污染生成。
- **生成幻觉**：模型在证据不足时仍会补全。
- **更新成本**：文档变更后索引和向量需要同步更新。

面试表达：

> 我理解 RAG 不是简单的“先搜一遍再让模型写”，而是把知识检索变成生成链路的一部分。真正落地时，关键不是有没有 RAG，而是切片、召回、重排、上下文拼装和生成约束这整条链路是否闭环。

## 2. 如何评估一个 RAG 系统是否真的 work？

核心回答：

> RAG 评估要拆成检索质量、生成质量和端到端质量三层，否则你无法判断问题到底出在检索还是生成。

评估维度：

1. **检索层**
   - Recall@K
   - Precision@K
   - MRR
   - nDCG
   - 命中文档是否包含答案证据

2. **生成层**
   - Faithfulness：回答是否忠于检索内容
   - Answer Relevance：回答是否真的回答了问题
   - Correctness：答案是否正确
   - Conciseness：是否啰嗦

3. **端到端**
   - 用户任务完成率
   - 人工修改率
   - 响应延迟
   - 成本

如何区分检索和生成：

- 如果检索根本没命中答案，先看召回。
- 如果证据命中了但回答错误，重点看生成。
- 如果检索对、生成对，但用户仍不满意，可能是提示词组织或表达不符合业务预期。

面试表达：

> 我不会只看 final answer 的对错，而是把 RAG 拆成检索、重排、拼上下文和生成四个阶段分别评估。这样才能知道是 chunk 策略有问题，还是 rerank 不行，还是模型在证据足够时仍然胡说。

## 3. 文档应该如何 chunk？如果输入不是 Markdown，或者不同文档类别格式不同，怎么处理？

核心回答：

> Chunk 不是按固定长度硬切，而是按文档结构、语义边界和后续检索目标来切。对于不同文档类型，应该先做结构化解析，再按标题、段落、列表、表格、代码块等边界切分，最后用长度约束做二次修正。

策略：

- **Markdown / 文档类**：按标题层级切分，保留标题路径。
- **PDF / Word**：先做版面解析，再按章节、段落、表格切分。
- **网页**：去掉导航和脚本，只保留正文块。
- **代码**：按函数、类、文件级切分。
- **表格**：按表头 + 行块切，保留列名语义。

关键原则：

- **保留上下文元数据**：标题、章节路径、页码、文档类型、更新时间。
- **Overlap 不是越大越好**：重叠主要用于跨段语义连续，通常只保留少量关键信息。
- **先结构化，再长度化**：先按语义边界切，再按 token 数修剪。

面试表达：

> 如果文档格式不同，我不会一刀切按字符长度切。我会先根据文档类型做结构化解析，比如 PDF 先识别标题、段落和表格，再把 chunk 和它所属章节路径一起存起来，这样检索结果才有可解释性。

## 4. 切片时 overlap 参数的作用是什么？怎么确定比例？

核心回答：

> overlap 的作用是避免关键信息刚好切断在两个 chunk 之间，特别适合定义、表格说明、步骤说明这类上下文连续的内容。但 overlap 过大也会引入重复噪声，降低检索效率。

怎么定：

- 经验上可以从 10% 到 20% 试起。
- 如果是强结构化文档，比如 FAQ、短说明，overlap 可小一些。
- 如果是长流程、技术方案、法律条款，overlap 可以大一点。
- 最终要结合召回率和重复率做 A/B 测试，而不是拍脑袋。

面试表达：

> overlap 解决的是“边界切断”问题，但它会增加重复内容，所以它本质是召回率和噪声的权衡。我的做法是先按文档类型设初始值，再用检索命中率和重复率来调。

## 5. 向量库检索出的 Top-K 结果，如果 K 过大有什么问题？

核心回答：

> K 过大不一定更好，因为会把无关结果也塞进上下文，增加 token 压力、干扰生成、拉低答案聚焦度，还会增加 rerank 和 prompt 成本。

具体影响：

- 上下文被噪声稀释。
- 关键信息被埋在中间。
- 模型容易被相似但错误的段落误导。
- 推理成本升高。

解决：

- 先召回较大 K，再用 Rerank 压缩到更小候选集。
- 用 MMR 去重，提高多样性。
- 对不同 query 动态调节 K。

## 6. 为什么在初筛召回之后，还要加 Rerank？它能解决什么问题？

核心回答：

> 向量召回解决“找得到”，Rerank 解决“排得准”。向量检索擅长语义近似，但在精排相关性、关键词对齐、字段约束和细粒度判断上不够强。

Rerank 的价值：

- 更细粒度地比较 query 和候选文本。
- 纠正向量召回的语义偏差。
- 把真正最相关的几条放到前面。
- 减少最终上下文噪声。

常见实现：

- Cross-Encoder Rerank
- 轻量排序模型
- LLM 作为 judge 做粗精排

面试表达：

> 我把召回和重排看成两级过滤。召回负责从海量文档里捞出“差不多相关”的候选，Rerank 再做精判断，尤其适合术语、编号、字段和上下文依赖强的场景。

## 7. Embedding 模型怎么选？稠密检索和稀疏检索分别适合什么？

核心回答：

> Embedding 模型的选择要看语言、领域、文本长度、查询类型和延迟约束。稠密检索适合语义相似，稀疏检索适合关键词精确匹配。实际系统里通常做混合检索。

选择原则：

- 中文场景优先选中文效果好的 embedding。
- 专业领域优先选经过领域适配的模型。
- 查询经常带术语、型号、代码时，稀疏检索更重要。
- 用户会用自然语言描述问题时，稠密检索更有效。
- 对延迟敏感时，模型大小和向量维度也要考虑。

稠密 vs 稀疏：

| 类型 | 优势 | 劣势 | 适合场景 |
|------|------|------|----------|
| 稠密检索 | 语义泛化强 | 精确匹配弱 | 问答、语义搜索 |
| 稀疏检索 | 关键词精确 | 语义泛化弱 | 型号、专有名词、代码、术语 |

面试表达：

> 我一般不会只押一个检索器。对于专业场景，密集向量负责语义召回，BM25 负责术语和精确词，最后再用 rerank 把结果收敛。

## 8. Milvus 里一般选什么索引？为什么？

核心回答：

> 选索引要看数据规模、召回要求、构建成本和查询延迟。常见选择包括 HNSW、IVF_FLAT、IVF_PQ 等。HNSW 查询快、召回高，适合在线检索；IVF 系列更适合大规模向量库和资源受限场景。

选型思路：

- **HNSW**
  - 优点：召回高、查询快、在线体验好。
  - 缺点：构建和内存开销较大。
- **IVF_FLAT**
  - 优点：在大规模下更容易控制资源。
  - 缺点：需要调 nlist / nprobe。
- **IVF_PQ**
  - 优点：压缩存储，降低内存占用。
  - 缺点：有近似损失。

面试表达：

> 如果是在线问答，我会优先关注召回和延迟，HNSW 往往更稳；如果是超大规模离线或资源紧张场景，IVF 系列更合适。核心不是某个算法名字，而是它和你的数据规模、更新频率、QPS 是否匹配。

## 9. 词项偏移或专业术语语义漂移，除了混合检索，还能怎么优化？

核心回答：

> 除了混合检索，还可以做领域 embedding 微调、query rewrite、术语词典增强、rerank 训练、文档规范化和知识治理。

可落地做法：

- 用领域数据微调 embedding。
- 为术语、缩写、别名建立词典。
- 对 query 做改写，补充上下文。
- 对文档做统一命名和结构化字段抽取。
- 用专门的 rerank 纠正语义偏差。

面试表达：

> 混合检索只能缓解一部分问题，如果专业术语在语料里语义漂移明显，就要考虑领域微调和知识治理，不然检索只是“看起来像”，不一定“真的对”。

## 10. RAG 如何判断是检索环节出问题，还是生成环节出问题？

核心回答：

> 最直接的方法是把链路拆开测。先看 gold answer 是否能被检索证据覆盖，再看生成答案是否忠于证据。如果证据都没召回到，就是检索问题；如果证据召回到了但回答偏了，就是生成或 prompt 问题。

排查顺序：

1. 检索命中率
2. Rerank 排序是否正确
3. 上下文拼接是否丢信息
4. 生成是否忠于上下文
5. 输出格式是否符合任务要求

可加的实验：

- 用人工 gold evidence 做对照。
- 固定检索结果，只换生成模型。
- 固定生成模型，只换检索策略。
- 分别测 recall、faithfulness、answer relevance。

## 11. 文档变更后，如何做增量索引避免全量重建？

核心回答：

> 增量索引的核心是识别变化范围，只重建受影响的 chunk 和向量，而不是全量重算。做法一般是给文档块加稳定 ID 和版本号，再根据 diff 计算新增、删除和更新部分。

做法：

- 文档结构切块后给每个 chunk 编码唯一 ID。
- 记录 chunk 的 hash、版本、来源页码。
- 新文档入库时先比对 hash。
- 变化的块重算 embedding 和索引。
- 未变化的块保留原向量。

## 12. HyDE 是什么？有什么优势？

核心回答：

> HyDE 是假设性文档嵌入。它先让模型根据问题生成一个“假想答案文档”，再对这段假想文档做 embedding，用来检索真实知识。它对模糊问题和短 query 往往比直接对问题做 embedding 更稳。

优势：

- 把稀疏问题转成更丰富的语义表达。
- 对 query 表述很短或很抽象时更有效。
- 常用于提升召回质量。

注意：

- 会增加一次生成成本。
- 假想文档如果偏了，也会影响召回。

## 13. 什么是 GraphRAG？为什么有时比普通 RAG 更好？

核心回答：

> GraphRAG 是把知识结构化成图，再借助图上的实体、关系和社区结构做检索与推理。它适合有强关联、多跳推理、跨文档依赖的场景。

适合场景：

- 人物关系、组织结构、供应链、代码依赖、复杂业务系统。
- 需要多跳关联的问答。

优势：

- 能显式表达实体关系。
- 能做多跳召回。
- 比纯向量检索更适合结构化知识。

局限：

- 构图和维护成本高。
- 更新频繁时治理复杂。

## 14. Agent 里的长短期记忆怎么设计？如何压缩和冲突更新？

核心回答：

> 我会把记忆分成短期会话记忆、长期事实记忆和结构化画像记忆三层。短期记忆保留最近上下文，长期记忆存关键事实，画像记忆存用户偏好、稳定约束和历史决策。冲突更新时优先保留最新、可信、可验证的信息。

设计思路：

- **短期**：最近若干轮原文对话。
- **长期**：重要事实、偏好、历史项目状态。
- **画像**：结构化字段，如角色、偏好、禁忌、常用工具。

压缩：

- 用摘要保留任务目标和决策结果。
- 用实体抽取把长文本转成结构化字段。
- 对重复事实做合并。

冲突处理：

- 新信息覆盖旧信息，但要保留版本和来源。
- 对有冲突的事实标记置信度。
- 必要时人工确认。

## 15. 多 Agent 架构比单 Agent 的优势是什么？Router 怎么分发？

核心回答：

> 多 Agent 的优势在于分工明确、能力隔离、任务可并行和易于扩展。Router 负责根据任务类型、上下文状态、工具可用性和置信度，把任务分给最合适的子 Agent。

适合场景：

- 一个 Agent 负责检索。
- 一个负责规划。
- 一个负责工具调用。
- 一个负责审查结果。

Router 规则：

- 基于任务分类。
- 基于意图识别。
- 基于阶段状态。
- 基于失败重试策略。

## 16. 什么是 Human-in-the-loop？如何设计人工审批断点？

核心回答：

> Human-in-the-loop 是把人工确认作为 Agent 决策链路中的安全阀。尤其在支付、删除、发布、发券、权限变更等高风险操作前，必须引入人工审批或二次确认。

设计原则：

- 高风险操作必须停。
- 低置信度输出必须停。
- 涉及不可逆动作必须停。
- 关键节点可配置。

实现方式：

- 设置审批状态机。
- 输出候选方案供人确认。
- 记录人工修改用于后续优化。

## 17. ReAct 和 CoT 的区别是什么？

核心回答：

> CoT 强调模型内部逐步推理，ReAct 则把“思考”和“行动”结合起来，让模型在推理过程中调用工具、观察环境，再继续推理。它更适合需要外部信息和多步交互的任务。

区别：

- CoT 更像纯思维链。
- ReAct 是思考 + 行动 + 观察循环。
- ReAct 适合搜索、工具调用、Agent 任务。

## 18. Function Call 的完整流程是什么？如何把自然语言转成结构化参数？

核心回答：

> Function Call 的流程是：先定义工具 schema，再由模型根据用户输入判断是否要调用工具，输出结构化参数，服务端校验参数后执行函数，最后把结果回传给模型进行最终回答。

流程：

1. 定义函数名、参数类型、必填字段。
2. 模型根据语义选择函数。
3. 输出 JSON 或结构化参数。
4. 服务端做 schema 校验和安全检查。
5. 真正调用外部系统。
6. 把工具返回结果再喂给模型总结。

注意：

- 参数幻觉要做校验。
- 工具调用失败要有 fallback。
- 不要把所有错误都交给模型自修。

## 19. MCP 的 schema 格式和协议大概包含什么？

核心回答：

> MCP 可以理解为让模型以标准协议发现和调用外部工具。它通常会定义工具的名称、描述、输入 schema、输出格式和调用约定，服务端再通过统一协议暴露资源、工具和提示模板。

常见内容：

- tool name
- description
- input schema
- output schema
- resources
- prompts
- capabilities

面试表达：

> MCP 的重点不是某个字段长什么样，而是它把工具发现、参数规范、资源访问和调用约定标准化了，这样不同客户端都能复用同一套工具能力。

## 20. Skill 和 MCP 有什么区别？

核心回答：

> Skill 更像“如何做某类任务”的能力包，强调行为模式、工作流和局部知识；MCP 更像“如何接工具”的协议层，强调让模型以统一方式访问外部资源和服务。

简单区分：

- **Skill**：方法论、流程、任务模板。
- **MCP**：工具发现和调用协议。

## 21. Agent 评估体系一般包括哪些维度？工具被多调用但不影响结果，怎么量化？

核心回答：

> Agent 评估不能只看最终答案，还要看规划、工具调用、成功率、延迟、冗余、稳定性和人类成本。工具多调用但无结果影响时，可以通过冗余调用率、无效调用率、平均步数和任务成功率联合描述。

指标：

- 任务成功率
- 规划正确率
- 工具调用成功率
- 平均步数
- 平均延迟
- 无效工具调用率
- 人工接管率

## 22. Agent 响应太慢，怎么优化？

核心回答：

> 优化思路是减少不必要的 LLM 调用、压缩上下文、并行工具调用、缓存高频结果、缩短检索链路和选择更快的推理框架。

可落地：

- 合并小步骤。
- 并行执行独立工具。
- 使用 streaming 输出。
- 缓存检索和固定指令。
- 对长文本先摘要再喂给模型。
- 用更轻的模型做路由和分类。

## 23. QA 业务型 Agent 和 DeepSearch Agent 有什么差别？

核心回答：

> QA 业务型 Agent 更像“按固定业务知识回答标准问题”，目标是稳定、可控和低风险；DeepSearch Agent 更像“带搜索和多步推理的深度研究员”，目标是尽可能挖掘更多证据并形成综合判断。

区别：

- QA 更强调标准答案和响应速度。
- DeepSearch 更强调广泛检索、证据整合和深度推理。
- QA 适合标准问答、FAQ、客服。
- DeepSearch 适合研究、分析、复杂问题。

## 24. 如果知识库内容过多，AI 也会有上下文压力，怎么裁剪或命中？

核心回答：

> 主要靠“分层索引 + 检索重排 + 摘要压缩 + 上下文缓存”。不是把所有知识一次塞进去，而是让系统先判断当前问题该走哪一层知识，再把少量高相关内容送给模型。

方法：

- 分层目录和标签。
- 按章节、实体、任务类型检索。
- 命中后做 rerank。
- 只保留必要证据片段。
- 对常用系统指令做缓存。

## 25. 如果检索到的知识是错的或者过期了，怎么治理？

核心回答：

> 要从知识治理而不是只从检索层解决。需要给文档加版本、时间戳、来源和置信度，对过期内容标记失效，并在索引更新时删除或降权旧内容。

治理方式：

- 版本管理
- 来源可追溯
- 过期标记
- 定期重建索引
- 人工审核高风险知识

## 26. 意图识别一般分哪几类？多意图怎么处理？

核心回答：

> 意图识别可以按业务动作、信息需求、情绪状态和风险等级来分。单意图场景可以做单标签分类，多意图场景更适合多标签分类或“主意图 + 辅意图”的结构化输出。

常见分类：

- 查询类：查资料、查订单、查库存。
- 操作类：创建、修改、删除、提交。
- 咨询类：解释规则、推荐方案。
- 投诉/情绪类：负面情绪、紧急求助。
- 高风险类：支付、退款、发券、权限变更。

多意图处理：

- 输出多个标签及置信度。
- 识别主意图和辅意图。
- 高风险意图优先拦截。
- 意图冲突时追问用户澄清。

## 27. 动态意图问题怎么处理？比如关键词含义随时间或热点变化

核心回答：

> 动态意图不能只靠静态分类器，需要结合时间、上下文、热词库、在线反馈和 RAG 更新机制。关键词含义变化时，要让系统能从近期语料和业务规则里补充最新解释。

落地方式：

- 热点词表定期更新。
- 对近期 query 做聚类。
- 引入时间衰减，让近期语料权重更高。
- RAG 召回最新业务文档。
- 低置信度触发人工确认或澄清。

## 28. RAG 在意图识别里有什么作用？

核心回答：

> RAG 可以把静态意图分类变成“基于最新业务知识的意图理解”。当意图定义、业务规则、活动名称经常变化时，RAG 能补充分类器不知道的新知识。

例子：

- 新活动上线后，用户说活动简称，分类器未必识别。
- RAG 可以召回活动规则文档，再辅助判断用户真实意图。

## 29. 大流量场景下，怎么利用 3B 模型效果，又不实时推理？

核心回答：

> 可以把 3B 模型用于离线标注、蒸馏、缓存、规则生成或 embedding 生成，线上用轻量模型、规则或缓存承接高频请求。

方案：

- 离线跑 3B 生成标签或规则。
- 蒸馏到小模型。
- 高频 query 结果缓存。
- 低频复杂问题再走实时模型。
- 用 3B 做离线特征生成。

## 30. 外部测评工具返回格式和大模型输入格式不匹配，如何自动映射？

核心回答：

> 先定义目标 schema，再写适配层把外部字段映射到标准字段。对可预测格式用规则和映射表，对半结构化内容可以用 LLM 做抽取，但最后必须经过 schema 校验。

步骤：

1. 定义统一输入 schema。
2. 为每个外部工具写 adapter。
3. 字段缺失时补默认值或标记 unknown。
4. 通过 JSON Schema / Pydantic 校验。
5. 校验失败进入人工或 fallback。

## 31. 用户长期画像和当前实时会话冲突时怎么办？

核心回答：

> 一般以当前明确表达优先，但不能直接删除长期画像。更合理的是给画像加时间戳、置信度和版本，实时会话作为高优先级临时状态，确认稳定后再更新长期记忆。

例子：

- 长期画像：用户喜欢简洁回答。
- 当前会话：用户说“这次请详细解释”。
- 系统应本轮详细解释，但长期画像不立即改成“总是喜欢详细”。

## 32. 如何避免模型过度依赖检索知识，导致回答生硬、缺乏共情？

核心回答：

> 检索知识应该作为事实依据，不应该完全决定语气和表达。可以把“事实证据”和“回复风格”分开控制：证据来自 RAG，表达由对话策略和用户状态决定。

做法：

- Prompt 中区分“依据”和“表达要求”。
- 对情绪类场景先回应情绪，再给事实。
- 只引用必要证据，不机械堆文档。
- 对缺证据内容明确说明不确定。

## 33. 如果检测到用户极端情绪，Agent 如何不中断对话流地干预？

核心回答：

> 应该先降低任务推进强度，转为安抚、确认风险、给出安全建议，并在高风险情况下引导用户联系人工或专业渠道。技术上可以用情绪识别节点触发安全策略，而不是直接中断。

流程：

1. 识别情绪和风险等级。
2. 低风险：共情回应 + 继续解决问题。
3. 中风险：放慢节奏 + 提供可执行建议。
4. 高风险：触发人工介入或安全提示。

## 34. 调用工具时出现参数幻觉、语法错误，怎么自动修正？

核心回答：

> 不能直接相信模型输出，要在工具调用前做 schema 校验、类型校验、必填字段校验和权限校验。错误可回传给模型让它修正，但要限制重试次数。

可落地机制：

- JSON Schema 校验。
- 参数白名单。
- dry-run。
- 自动重试一次或两次。
- 多次失败转人工或 fallback。

## 35. Multi-Agent 中心化编排和点对点架构有什么区别？

核心回答：

> 中心化编排由一个主控节点调度所有子 Agent，优点是可控、可观测、易审计；点对点架构让 Agent 之间直接通信，灵活但更难控制。

对比：

- 中心化：适合业务系统、权限敏感、流程明确。
- 点对点：适合探索型协作、开放任务，但风险更高。

## 36. Agent 的 Self-Reflection 机制底层原理是什么？

核心回答：

> Self-Reflection 是让模型对自己的中间结果或最终输出做二次审查，检查是否满足目标、是否缺少证据、是否有逻辑错误。它本质上是引入一个评审角色或验证步骤。

注意：

- 不能把反思当成绝对正确。
- 高风险场景仍需要规则校验或人工确认。

## 37. 单一 Skill 模块应该怎么设计？

核心回答：

> 一个 Skill 应该只解决一类明确任务，包含触发条件、输入输出、执行步骤、失败处理和边界限制。设计目标是让 Agent 在对应场景下稳定复用，而不是每次重新想流程。

结构：

- 适用场景
- 输入要求
- 执行步骤
- 工具依赖
- 输出格式
- 错误处理

## 38. LangGraph 里的 State 怎么定义和流转？节点多了如何避免 State 膨胀？

核心回答：

> LangGraph 的 State 是多节点共享的任务状态对象，节点读取和更新 State，边根据条件决定下一步。State 设计要尽量结构化和最小化，不要把所有历史都塞进去。

避免膨胀：

- 只保存必要字段。
- 大文本外置存储，只在 State 里放引用。
- 对历史消息定期摘要。
- 分离短期 state 和长期 memory。

## 39. 主 Agent 和子 Agent 共用同一个上下文吗？

核心回答：

> 不一定。更好的设计是共享任务目标和必要状态，但每个子 Agent 只拿自己需要的上下文。否则上下文会过长，也容易互相污染。

实践：

- 主 Agent 维护全局状态。
- 子 Agent 获取局部上下文。
- 子 Agent 输出结构化结果回写。

## 40. 什么是渐进式披露？

核心回答：

> 渐进式披露是指不要一次性把所有复杂信息展示或交给用户，而是按任务阶段逐步展开。Agent 产品里可以先给结论，再允许用户展开证据、步骤或工具调用过程。

价值：

- 降低认知负担。
- 保留可解释性。
- 避免界面被中间过程淹没。

## 41. 如何保障自然语言任务描述能转成稳定可靠的执行路径？

核心回答：

> 不能直接从自然语言跳到执行，要经过意图识别、参数抽取、计划生成、工具校验、权限检查和执行确认。高风险动作还要人工审批。

链路：

```text
用户输入 -> 意图识别 -> 参数抽取 -> 计划生成 -> 工具校验 -> 执行 -> 结果验证
```

## 42. 上下文缓存是什么？在 Agent 里有什么价值？

核心回答：

> 上下文缓存是把频繁重复的系统指令、工具说明、知识片段或前缀 prompt 缓存起来，减少重复传输和计算。对频繁调用同一 Agent 的场景，可以显著降低延迟和成本。

### A2. BM25 公式和为什么比 TF-IDF 更好

BM25 常见形式：

```text
score(q, d) = \sum_{t in q} IDF(t) *
              (f(t,d) * (k1 + 1)) /
              (f(t,d) + k1 * (1 - b + b * |d| / avgdl))
```

核心变量：

- `f(t,d)`：词 t 在文档 d 中出现次数。
- `|d|`：文档长度。
- `avgdl`：平均文档长度。
- `k1`：控制词频饱和。
- `b`：控制文档长度归一化。

相比 TF-IDF 的改进：

- 词频不是无限线性增加，而是会饱和。
- 对长文档做长度归一化。
- 在关键词、型号、术语检索中非常强。

### A3. Dense / Sparse / Hybrid 怎么讲清楚

| 检索方式 | 原理 | 优势 | 缺点 | 适合场景 |
|----------|------|------|------|----------|
| Sparse | 关键词匹配，如 BM25 | 精确、可解释 | 不懂语义改写 | 型号、术语、代码 |
| Dense | embedding 语义向量 | 语义泛化强 | 可能错过精确词 | 自然语言问答 |
| Hybrid | 两路召回融合 | 兼顾精确和语义 | 系统复杂 | 企业知识库 |

RRF 融合可以这样解释：

```text
RRF(d) = \sum_i 1 / (k + rank_i(d))
```

它不直接比较不同检索器的原始分数，而是融合排名，更稳定。

### A4. Rerank 为什么有效

Embedding 召回通常是“向量级粗筛”，Rerank 是“query-doc 成对精排”。

Cross-Encoder Rerank 输入一般是：

```text
[CLS] query [SEP] document [SEP]
```

模型直接判断二者相关性，所以比单独向量相似度更细。

可以这样答：

> 向量检索提前把全库缩小到 Top-100，Rerank 再从 Top-100 里选 Top-5。这样既控制成本，又提高最终上下文质量。

### A5. Chunk 策略细节

一个好 chunk 通常包含：

- 正文内容。
- 标题路径。
- 文档来源。
- 页码 / 章节。
- 更新时间。
- 文档类型。

示例结构：

```json
{

  "metadata": {
    "title_path": ["产品手册", "库存查询", "异常处理"],
    "page": 12,

  }
}
```

### A6. RAG 判断问题在哪一环的排查表

| 现象 | 可能问题 | 排查方式 |
|------|----------|----------|
| 答案完全错 | 没召回证据 | 看 Recall@K |
| 证据召回了但答错 | 生成不忠实 | 看 Faithfulness |
| 答非所问 | query 理解或 prompt 问题 | 看 Answer Relevance |
| 答案过长 | context 噪声太多 | 调 K、rerank、压缩 |
| 老答案覆盖新答案 | 时间衰减不足 | 加版本和更新时间权重 |

### A7. Agent 与 Workflow 的选择标准

| 任务类型 | 更适合 Workflow | 更适合 Agent |
|----------|-----------------|--------------|
| 步骤固定 | 是 | 否 |
| 结果可预测 | 是 | 否 |
| 需要探索 | 否 | 是 |
| 工具选择动态 | 否 | 是 |
| 高风险审批 | Workflow + HITL | Agent 需强约束 |

面试表达：

> 我不会所有任务都上自主 Agent。步骤固定、风险高的任务用 Workflow 更稳；任务开放、工具选择不确定、需要多步探索时再用 Agent。

### A8. Tool Calling 的工程安全清单

工具调用一定要有：

- Schema 校验。
- 参数类型校验。
- 权限校验。
- dry-run。
- 超时。
- 重试上限。
- 幂等设计。
- 审计日志。

错误修正流程：

```text
模型输出参数 -> schema 校验失败 -> 把错误原因回传模型 -> 模型修正
             -> 再次失败 -> fallback / 人工介入
```

### A9. Agent Memory 的三层模型

```text
短期记忆：最近对话原文，负责连续性
工作记忆：当前任务状态，负责执行过程
长期记忆：稳定事实/偏好/项目知识，负责跨会话复用
```

冲突更新建议：

- 当前会话明确表达优先。
- 长期偏好不被一次临时请求覆盖。
- 关键事实保留来源和时间。
- 高风险画像更新需要确认。

### A10. Agent 评估指标详细解释

| 指标 | 含义 | 适用问题 |
|------|------|----------|
| Task Success Rate | 任务最终完成率 | Agent 是否真的做成 |
| Tool Success Rate | 工具调用成功率 | 工具链是否稳定 |
| Invalid Tool Call Rate | 无效工具调用率 | 是否乱调工具 |
| Step Efficiency | 平均完成步数 | 是否绕路 |
| Human Takeover Rate | 人工接管率 | 自动化是否可靠 |
| Hallucination Rate | 幻觉率 | 回答是否编造 |
| Latency P95/P99 | 尾延迟 | 用户体验 |

如果“工具多调用但不影响最终结果”，可以用：

```text
Redundant Tool Call Rate = 无收益工具调用次数 / 总工具调用次数
```

```python
from typing import TypedDict, List, Optional

class AgentState(TypedDict):
```

### A12. Human-in-the-loop 断点设计

- 低置信度决策。
