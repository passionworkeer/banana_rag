Agent：让模型从“回答问题”变成“完成任务”

Agent 的核心是闭环：理解目标、规划步骤、调用工具、观察结果、更新状态、必要时请求人工确认。面试时不要只说“Agent 会调用工具”，要能讲清楚状态、记忆、路由、安全和评估。

Agent 的效用函数

utility(action) = taskrelevance + confidence - toolcost - riskpenalty - latencypenalty
这个公式不是固定模型，而是面试里解释“为什么要规划、为什么要路由、为什么要限制高风险动作”的通用框架。
这个公式不是固定算法，而是面试里解释“为什么要路由、为什么要人工审批、为什么不能乱调用工具”的框架。

知识点拆解

1. Function Call

模型不直接执行工具，而是输出结构化参数；服务端校验 schema、权限和风险后，再决定是否执行。

2. Memory

短期记忆保留最近对话，工作记忆维护当前任务状态，长期记忆保存稳定偏好和事实。

3. Router

根据意图、置信度、工具能力、风险等级，把任务分到不同工具或子 Agent。

4. HITL

支付、删除、发券、发布、权限变更这类不可逆动作必须有人工确认断点。

面试回答模板

“我理解 Agent 不是简单套一个大模型，而是一个执行闭环。它先理解任务，再规划步骤，调用工具，观察结果并更新状态。高风险节点需要人工审批，低置信度结果需要反思或 fallback。”

常见追问与回答

任务什么时候用 Workflow，什么时候用 Agent？

如果步骤固定、风险高、结果可预测，优先 Workflow；如果任务需要探索、多工具协作、步骤会根据中间结果变化，再用 Agent。很多生产系统会采用“Workflow + 局部 Agent”的混合结构。

工具参数幻觉怎么处理？

不能直接信模型输出，必须做 schema 校验、类型校验、权限校验和幂等控制。参数不合法就让模型基于错误信息修正，超过重试次数就 fallback 或人工介入。

长期记忆和当前会话冲突怎么办？

当前明确表达优先，但只影响本轮执行，不要立刻覆盖长期画像。更稳妥的做法是给记忆加时间戳、来源和置信度，确认稳定后再更新长期状态。

Agent 系统怎么评估规划能力和幻觉率？

规划能力可以看任务完成率、平均步数和计划正确率；幻觉率可以看无依据回答比例、工具调用伪造率和事实一致性。最好把检索、工具调用和最终答案分别评估。
