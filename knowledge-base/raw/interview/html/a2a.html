A2A：让 Agent 之间像 HTTP 一样对话

Agent-to-Agent Protocol，Google 2025 年开源的 Agent 互联协议。核心思想是：每个 Agent 暴露一份"名片"（Agent Card），其他 Agent 通过标准化信封（JSON-RPC over HTTP/SSE）发现并调用它。A2A 解决的是"Agent 之间的会话"问题，与 MCP（"Agent 怎么调工具"）正交互补。

一、A2A 三层架构

二、Agent Card 示例

{
  "name": "order-agent",
  "description": "查询与处理订单状态",
  "url": "https://agents.example.com/order",
  "version": "1.0.0",
  "skills": [
    { "id": "lookup", "name": "查订单" },
    { "id": "refund", "name": "申请退款" }
  ],
  "authentication": {
    "schemes": ["bearer"]
  },
  "defaultInputModes": ["text", "file"],
  "defaultOutputModes": ["text", "data"]
}

Agent Card 是 Agent 的"招聘简历"——告诉其他 Agent 自己会什么、怎么对话、需要什么鉴权。其他 Agent 拿到后决定"是否要把任务发给你"。

三、Task 状态机

状态含义
submitted任务已接收、待处理
working正在执行（可能产生 Artifact 增量）
input-required需要客户端补料（追问 / 文件）
completed成功，Artifact 为最终结果
failed出错，带错误码与说明
canceled被主动取消
状态机的关键：客户端可以随时 tasks/get 拉取、也可以用 SSE 订阅。这是 A2A 与"一次性 HTTP 调用"最大的区别——它把 Agent 任务建模成"长事务"。

四、消息与 Artifact 结构

{
  "id": "task-001",
  "status": "working",
  "messages": [
    {
      "role": "user",
      "parts": [
        { "type": "text", "text": "查一下订单 20240512001 的状态" },
        { "type": "file", "file": { "mimeType": "image/png", "data": "" } }
      ]
    }
  ],
  "artifacts": [
    {
      "name": "result",
      "parts": [
        { "type": "data", "data": { "status": "shipped", "eta": "2024-05-13" } }
      ]
    }
  ]
}

Part 是 A2A 的"多模态原子"——一段文本、一个文件、一段结构化数据。客户端和远端 Agent 都用同样的 Part 数组组装消息，使"图片+文字"或"表格+追问"成为一等公民。

六、A2A 适用场景

  • 跨厂商协作：蕉内的客服 Agent 调顺丰的物流 Agent 拿实时轨迹
  • 企业内部门协同：HR Agent ↔ 财务 Agent ↔ IT Agent 串成审批流
  • 长任务外包：把"做一份竞品分析报告"委派给垂直 Agent，跨小时/天
  • 不确定的发现：开放 Agent 生态中先查 Agent Card 再决定要不要调用
不适用：单 Agent 内部的工具调用（用 MCP）、实时流式数据消费（用 WebSocket / gRPC streaming）、跨公司数据合规敏感场景（要先解决数据出域问题）。

七、面试 FAQ

Q1：A2A 和 MCP 必须一起用吗？

A：不必。A2A 解决 Agent ↔ Agent；MCP 解决 Agent ↔ Tool。两者正交。一个最小 A2A Agent 不需要任何 MCP；一个纯本地 Agent 也不需要 A2A。生产复杂系统一般两者都上。

Q2：Agent Card 怎么防止伪造？

A：三层防护：① HTTPS + mTLS 保护传输；② Agent Card URL 必须可控（公司域名下）；③ 鉴权 schemes 写在 Card 里，调用时必须通过对应身份验证。开放生态中还会引入"Agent 目录服务"做第三方背书。

Q3：流式场景怎么处理大量 Artifact？

A：A2A 把 Artifact 设计为"可分块 + 可索引"，SSE 事件中带 artifactId + chunkIndex，客户端按顺序组装。也可以让客户端先 GET artifact 看大小，决定是流式还是拉取。

Q4：A2A 的 input-required 状态具体怎么用？

A：远端 Agent 在执行中发现"需要更多信息"（比如用户没给订单号）时进入 input-required，附上 question part。客户端补料后通过 tasks/send 续传。适合"多轮反问"的复杂任务。

Q5：A2A 和 HTTP API 区别在哪？

A：技术上 A2A 是 HTTP+JSON-RPC+SSE；本质区别是"语义层"——A2A 把"任务"作为一等公民（带生命周期、状态机、长事务），并标准化了 Agent 之间的发现、协商、续传、流式语义。普通 HTTP API 仍可被 A2A Agent 调用（当 Tool 用）。

Q6：怎么选 A2A、ACP、A2A-ANP？

A：A2A（Google）— 主流、生态最广、JSON-RPC 风格；ACP（IBM 主导）— REST 风格，更接近 Web API；ANP（开源社区）— 点对点、去中心化。多数企业落地选 A2A，参考实现最多。

Q7：A2A 调用如何计费和限流？

A：A2A 协议本身没规定，但生产中常见做法：① Agent Card 里声明 rate limit + 计费策略；② 网关层做 token bucket 限流；③ 任务级 usage 埋点，结算按 task / token 颗粒。开放生态可结合"Agent 目录服务"做信用体系。

Q8：A2A 的失败怎么传播？

A：Task 进入 failed 状态，body 里含 error code（标准错误码集）+ message。客户端可以重试 / fallback / 升级人工。链路长时建议把上游 task_id 透传到下游，便于全链路追踪。

八、回答模板与加分项

30 秒电梯版

A2A 是 Google 主导的 Agent 互联协议，让不同厂商的 Agent 像 HTTP 服务一样被发现和调用。核心是 Agent Card（能力描述）+ JSON-RPC 任务提交 + SSE 流式响应。Task 有完整生命周期（submitted → working → input-required → completed）。A2A 和 MCP 正交：MCP 让 Agent 调工具，A2A 让 Agent 调 Agent。

5 分钟深入版

从动机（"我的 Agent 怎么调别人的 Agent"）→ 协议分层（Discovery / Submit / Stream / Auth）→ Agent Card 设计 → Task 状态机 → 消息/Artifact 结构 → 与 MCP 的边界 → 生产级考量（鉴权 / 限流 / 失败传播）。能讲清楚"为什么 A2A 单独成协议而不直接用 HTTP API"是拉开差距的关键。

加分：实战选型

讲一次"为什么不用 HTTP API 而上 A2A"——比如需要长任务（订单处理跨多小时）、需要反问补料、需要流式 artifact、需要跨厂商统一鉴权，普通 REST 都要重造轮子，A2A 已经有现成规范。

加分：知道 A2A 局限

A2A 不是银弹：① 开放生态下 Agent Card 真实性需要信任链；② 流式 SSE 在企业 NAT/代理下经常断；③ 状态机对短任务反而是负担（同步 API 更直接）；④ 跨公司合规（GDPR / 数据出域）协议层解决不了。要诚实说"这些场景我了解但生产经验有限"。
