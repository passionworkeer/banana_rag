一、为什么需要多 Agent

  • 单 Agent 上下文压力大（10+ 工具 / 多领域知识塞一个 prompt）
  • 专业度不够（一个 Agent 难以精通所有任务）
  • 错误风险集中（关键任务失败影响全流程）
  • 无法并行（单 Agent 必须串行处理多任务）
  • 审计与可解释性差（决策散在多步 thought 里）
判断口诀：任务能拆成 ≥2 个"独立子任务"、每个子任务需要不同工具/知识/风格。简单 QA 单 Agent 就够；多步骤 / 多领域 / 多模态 / 需要审计考虑上 Multi-Agent。

三、Router 架构图（最常见模式）

User 提问经 Router 分类后分发到对应 Sub-Agent 执行；Sub-Agent 共享 Shared Memory 读上下文；结果回传 Router 合并答复。各 Agent 独立 prompt、独立工具集，错误隔离。

五、3 类通信模式

  • 集中式 (Hub-and-Spoke)：所有 Agent 通过 Planner 中转，适合强结构任务
  • 点对点 (Peer-to-Peer)：Agent 直接互发消息，适合去中心化任务
  • 共享黑板 (Blackboard)：所有 Agent 读写共享 Memory，适合信息密集任务
通信模式决定可扩展性：集中式易调试但 Planner 成瓶颈；点对点灵活但调试难；黑板适合"事实 + 推理"类任务（如多专家会诊）。

七、4 种共识 / 仲裁机制

  • 投票 (Voting)：多 Agent 各自答，最后多数票胜出
  • 辩论 (Debate)：两个 Agent 正反辩论，Judge 判胜负
  • 迭代修订 (Revise)：Writer → Critic → Writer 循环到满意
  • Leader 仲裁 (Hierarchical)：Leader Agent 收各 Agent 答案后决策
实际中"Leader 仲裁 + Critic 修订"是最稳的组合：保留集中式可控，又有多视角反馈。

两种路由实现

① 规则路由：关键词匹配 / 正则 / 决策表，零 LLM 成本（<1ms）

② LLM 路由：调用小模型（GPT-3.5 / Qwen-7B）做意图分类，准确率高但 ~200ms

生产经验：先规则路由（80% 场景命中），不确定时降级到 LLM 路由；置信度低时兜底到 General Agent。

Router 输出格式： route = Router.classify(user_input) → "design" | "data" | "service" | "general"

Sub-Agent 设计要点

十、CrewAI 代码示例

from crewai import Agent, Task, Crew

researcher = Agent(
  role="研究员",
  goal="收集主题相关的事实和证据",
  backstory="资深行业分析师",
  tools=[search_tool, rag_tool]
)

writer = Agent(
  role="撰稿人",
  goal="基于研究结果撰写结构化报告",
  backstory="擅长把复杂信息讲清楚的编辑"
)

critic = Agent(
  role="审稿人",
  goal="发现报告事实错误和结构问题",
  backstory="严格的质量审查专家"
)

t1 = Task(description="研究 XX 主题", agent=researcher)
t2 = Task(description="基于研究撰写报告", agent=writer)
t3 = Task(description="审稿 + 反馈修订", agent=critic)

crew = Crew(agents=[researcher, writer, critic],
            tasks=[t1, t2, t3], verbose=True)
crew.kickoff()

决策冲突解决

  • 优先级：业务规则定义谁优先（如客服 Agent 优先于通用 Agent）
  • 投票：多 Agent 多数票决定（Debate 模式）
  • Supervisor 仲裁：监控 Agent 看完整上下文后决定
  • 置信度：每个 Agent 输出置信度，取最高

通信方式选型

  • 消息队列（Redis Stream / Kafka）：异步、解耦、可扩展
  • 共享状态（MemGPT / 共享向量库）：低延迟、状态一致
  • 直接调用（HTTP / RPC）：同步、简单但耦合

十一、项目落地

  • 蕉内实际：AI 数字员工多场景分流（设计 / 数据 / 客服）— Router 根据用户提问意图分类，分发到 Design / Data / Service 三个 Sub-Agent，Shared Memory 记录用户偏好跨场景复用
  • 假设场景：蕉内数字员工升级版 — 入口 Router 分类后，复杂任务交给 Supervisor 协调多 Agent 协作（如新品上市：Design 写文案 + Data 算库存 + Service 准备话术）
  • 简历表达：多 Agent 架构 / Router 设计 / 决策冲突解决 / 跨 Agent 共享记忆

十二、面试 FAQ

Q1：单 Agent 什么时候不够用？

A：四个信号：任务超过 10 步（上下文爆炸）、跨多个领域（设计 + 数据 + 客服一锅端）、错误成本高（关键任务失败影响业务）、需要并行（多任务并发）。任一信号明显时考虑多 Agent。

Q2：Multi-Agent 比单 Agent 强在哪？

A：3 个核心收益：① 角色分工让每个 Agent 只需"专精"——可换用更小模型、prompt 更短、效果更稳；② 错误隔离——一个 Agent 错不会拖垮全局；③ 视角多样——多个 Critic 提供不同反馈。但代价是通信开销、调试难度、token 成本线性增长。

Q3：Router 怎么设计？

A：两种实现：规则路由（关键词 / 正则 / 决策表，零 LLM 成本、<1ms、规则易维护）、LLM 路由（用小模型做意图分类，准确率高、~200ms、需考虑成本）。生产中常组合：先规则 80% 命中、不确定降级到 LLM、置信度低兜底到 General Agent。

Q4：Agent 间决策冲突怎么办？

A：四种机制：优先级（业务规则）、投票（多 Agent 多数票）、Supervisor 仲裁（看全局后决定）、置信度（取最高）。生产经验：优先级 + 置信度组合兜底，高风险场景用 Supervisor 仲裁。

Q5：AutoGen / CrewAI / LangGraph 选哪个？

A：研究/探索 → AutoGen（灵活、对话驱动）；业务流程化 → CrewAI（简单、声明式）；生产复杂状态机 → LangGraph（强状态控制、可观测）。国内业务多从 CrewAI / LangGraph 起步，AutoGen 多用于研究项目。

Q6：Multi-Agent 怎么调试？

A：3 个工具：① 消息 trace（每条消息谁发谁收 + 完整内容）；② 各 Agent 独立 eval（每个角色单独看完成率、正确率）；③ 失败 case 分类（通信失败 / 任务失败 / 协调失败）。LangGraph + LangSmith 是目前最完善的调试栈。

Q7：Multi-Agent token 成本怎么控？

A：4 个手段：① 给每个 Agent 设 token 配额和单步上限；② 共享 context 摘要而非全文；③ 简单步骤用小模型（Haiku）；④ 并行调用减少总时长。生产中 1 个 5-Agent 任务的 token 成本是单 Agent 的 3-8 倍常见。

Q8：Multi-Agent 死循环怎么办？

A：4 层防御：① Planner 设定最大轮次；② Critic 检测"重复内容 / 反复争论"时强制终止；③ Leader Agent 有终止权；④ 全局超时（按 wall time）。LangGraph 用 max_iterations、AutoGen 用 is_termination_msg。

Q9：Multi-Agent 评估怎么搞？

A：3 层：① 端到端：最终输出质量（人工 + LLM-as-Judge）；② 过程：每步是否合理、各 Agent 完成率；③ 通信：消息数、平均轮次、deadlock 率。和单 Agent 不同，必须监控"谁和谁说话"和"为什么停"。

Q10：怎么避免"领导独大"反模式？

A：典型反模式：Planner 越来越像万能胶水，把所有任务都自己干。解法：① Planner 只做拆解和路由，不做内容生成；② 各 Agent 有强系统 prompt 限定职责；③ 加 Critic 监控 Planner 是否越权；④ 定期 review Planner 决策。

回答模板与加分项

30 秒电梯版

面试开场可以这样讲：多 Agent 架构用 Router 把任务分发给专业 Sub-Agent，降低单 Agent 上下文压力、隔离错误。常见 5 类模式：Router（分发）、Supervisor（协调）、Debate（投票）、Handoff（动态交接）、Hierarchical（分层）。6 类角色：Planner / Researcher / Coder / Writer / Critic / Verifier。3 类通信：集中式 / 点对点 / 黑板。3 框架：AutoGen（研究）、CrewAI（业务流）、LangGraph（生产状态机）。

5 分钟深入版

从单 Agent 痛点 → 多 Agent 架构 → 5 类模式对比 → 6 类角色职责 → 3 类通信方式 → 3 框架对比 → 4 种共识机制 → 实际项目落地 → 4 类典型问题（成本 / 死循环 / 调试 / 集权）→ 评估方法。能讲清"为什么 Leader 仲裁 + Critic 修订最稳"、"为什么 AutoGen 不适合生产状态机"，立刻显得有真经验。

加分：知道多 Agent 的局限

多 Agent 不是银弹：token 成本高（多轮通信，3-8x）、延迟增加（多次 LLM 调用）、调试复杂（决策分散）、可能出现"死锁"（Agent 间互等）、"领导独大"（Planner 包揽所有任务）。建议结合"独立上下文 + 压缩中间结果 + 小模型分工 + 优雅降级"四件套缓解。

加分：项目案例

讲一次"为什么从单 Agent 切到 Multi-Agent"——比如客服 Agent 早期单 Agent 既要查订单、又要回答政策、又要写工单，prompt 越加越长、效果下降；拆成 Researcher + Writer + Critic 后，每个 Agent 系统 prompt 控制在 200 token 内，整体完成率 +20%、token 成本 -30%。

架构选型什么时候用多 Agent？答"四个信号"：任务超 10 步、跨多个领域、错误成本高、需要并行。任一明显时考虑多 Agent；否则单 Agent + 好工具更稳。多 Agent 不等于更好，要看场景。
