一、为什么需要专门的推理引擎

  • Naive HuggingFace generate()：batch=1、不批处理、KV-Cache 内存碎片化、显存浪费 60%+。
  • 推理引擎三大核心优化：①连续批处理（Continuous Batching，新请求随时加入）；②PagedAttention（KV-Cache 分页管理，显存利用率从 20% → 90%+）；③Kernel Fusion（FlashAttention、PagedAttention 内核）。
  • 典型收益：vLLM 比 HF Transformers throughput 提升 14-24x（LLaMA-7B, A100）；TGI 在 H100 上达 12,000+ tokens/s。
  • OpenAI 兼容：现代推理引擎都支持 /v1/chat/completions，现有应用零代码迁移。
  • 量化集成：AWQ / GPTQ / FP8 / INT4 一行参数启用，吞吐再翻 2-4x。
判断口诀：研究实验用 HF Transformers；生产高吞吐用 vLLM / TGI / TensorRT-LLM；NVIDIA 极致优化用 TensorRT-LLM；本地开发用 Ollama / LM Studio；企业级多模型编排用 Triton / BentoML。

三、vLLM 架构图（Continuous Batching + PagedAttention）

请求进入 Scheduler → Block Manager 按 Block 分配 KV-Cache（不预分配整段）→ Worker 池执行 attention → 完成序列的块立即归还 Free List → 新请求可立即复用。显存利用率从 20% 提升到 90%+。

四、TensorRT-LLM 优化流水线

TensorRT-LLM 把模型编译成 TensorRT Engine（.plan 文件），离线做算子融合 + 内核调优 + 量化；运行时用 Triton 服务器加载，支持 In-flight Batching 在 token 级调度，多 GPU 张量并行。

六、vLLM 实战代码

# 服务端启动
python -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-3-8B-Instruct \
  --tensor-parallel-size 2 \
  --gpu-memory-utilization 0.92 \
  --max-model-len 8192 \
  --quantization awq \
  --dtype float16

# 客户端（OpenAI SDK 直接复用）
from openai import OpenAI
client = OpenAI(
  base_url="http://localhost:8000/v1",
  api_key="EMPTY",
)
resp = client.chat.completions.create(
  model="meta-llama/Llama-3-8B-Instruct",
  messages=[{"role":"user","content":"你好"}],
  stream=True, temperature=0.7,
)
for chunk in resp:
  print(chunk.choices[0].delta.content, end="")

现有 OpenAI 客户端代码零修改，只需换 base_url。支持 AWQ/GPTQ/FP8 一行启用。

七、TensorRT-LLM 编译 + 部署

# 1. 转模型为 TensorRT-LLM 格式
python convert.py --model_dir llama-3-8b \
  --output_dir trt_engines/llama3-8b-fp16 \
  --dtype float16 --tp_size 2

# 2. 编译 engine（耗时数分钟）
trtllm-build --checkpoint_dir trt_engines/llama3-8b-fp16 \
  --output_dir trt_engines/llama3-8b-engine \
  --max_batch_size 64 --max_input_len 4096

# 3. Triton 部署
docker run --gpus all -p 8000:8000 \
  -v $PWD/trt_engines:/models \
  nvcr.io/nvidia/tritonserver:24.08-trtllm-python-py3 \
  tritonserver --model-repository=/models

# 4. 性能：H100 上达 8000+ tokens/s/QPS

十二、10 条面试 FAQ

1. vLLM 为什么快？

三个核心：①PagedAttention（KV-Cache 分页，显存利用率 20%→90%）；②连续批处理（新请求随时加入，结束随时退出）；③CUDA Graph + FlashAttention（kernel 优化）。综合 14-24x 收益。

2. Ollama 适合生产吗？

小规模 / 内部工具可以，大流量生产不建议。生产推荐 vLLM / TGI / TensorRT-LLM，支持高并发、监控、自动扩缩容。

3. TensorRT-LLM 和 vLLM 选哪个？

追求极致低延迟 + NVIDIA GPU选 TensorRT-LLM（编译复杂、性能极致）；追求通用性 + 快速上线选 vLLM（PagedAttention 开箱即用、生态最活跃）。

4. PagedAttention 解决了什么问题？

传统 KV-Cache 连续预分配导致严重碎片化和浪费（最长序列决定显存占用）。PagedAttention 按 Block（16 token）分页，按需分配，逻辑连续 / 物理不连续。

5. 连续批处理 vs 静态批处理？

静态批处理：等齐一个 batch 才推理，长尾请求拖慢整体；连续批处理：每步推理后调度器决定下一批，结束的请求立即退出，新请求立即加入，吞吐提升 2-4x。

6. AWQ / GPTQ / FP8 怎么选？

AWQ：激活感知权重量化，4-bit 几乎无损；GPTQ：训练后量化，通用性强；FP8：H100 原生支持，速度损失小。生产推荐 AWQ-4bit。

7. Triton 是什么定位？

通用模型服务器，支持 TF/PyTorch/ONNX/TensorRT 多后端，提供动态批处理、模型仓库、A/B Test、Metrics。是大厂多模型生产编排首选。

8. SGLang 的 RadixAttention 是什么？

用 Radix Tree 索引所有请求的 KV-Cache，自动识别共享前缀（如 system prompt / few-shot 示例），命中则复用，未命中才重新计算。Tree 结构的 prefix sharing 比 LRU 更高效。

9. 本地 GPU 显存不够怎么办？

三招：①量化（GGUF Q4 / AWQ-4bit，显存省 4-8x）；②Offloading（CPU + GPU 混合，llama.cpp 支持）；③多卡切分（Tensor Parallel，vLLM / TensorRT-LLM 支持）。

10. 推理引擎怎么监控？

vLLM 暴露 /metrics Prometheus 端点；TensorRT-LLM 通过 Triton 集成；关键指标：throughput / latency p50/p99 / GPU util / KV-Cache usage / queue length。接 Grafana 做看板。
