一、推理优化技术栈

  • 推理瓶颈：
    • 显存：KV Cache 占大头（7B 模型 + seq 4k + batch 32 ≈ 32GB）
    • 计算：GEMM 算力（FP16 矩阵乘）和 attention 计算（decode 阶段 O(seq_len)）
    • 带宽：HBM 带宽是 decode 阶段瓶颈（每 token 要读 14GB+ 权重）
  • Continuous Batching（连续批处理）：
    • 传统 Static Batching：等最慢请求完成才返回（GPU 空转）
    • Continuous Batching：动态拼批，新请求插队到当前 batch 空位，迭代级调度
    • 效果：GPU 利用率从 30% 提升到 70%+，吞吐量翻倍
  • PagedAttention（vLLM 核心）：
    • 原理：把 KV Cache 分成固定大小页（block），按需分配，类似 OS 虚拟内存分页
    • 效果：显存碎片从 60%+ 降到 <5%，batch size 可扩大 4-24x
    • 对应论文：vLLM SOSP 2023
  • SGLang RadixAttention：
    • 原理：基于前缀树（Radix Tree）复用多请求共享的 KV 段
    • 优势：复杂 prompt 模板（few-shot / 工具描述）天然复用，命中率 30-70%
    • 对应论文：SGLang NSDI 2024
  • 三种并行策略：
    • Tensor Parallel (TP)：层内切分到多卡（多头注意力切分头、MLP 切分列），需要卡间通信（NCCL）
    • Pipeline Parallel (PP)：按层切分到多卡（前 K 层卡 A，后 L 层卡 B），微批次流水
    • Data Parallel (DP)：多副本并行（同一模型跑在不同请求上），无通信
  • 框架选型：vLLM（通用首选）、SGLang（复杂 prompt 优选）、TensorRT-LLM（极致性能）、LMDeploy（轻量）

二、推理流水线

推理分 Prefill（处理 prompt，并行）和 Decode（逐 token 生成，受 HBM 带宽限制）两个阶段。PagedAttention 减少显存碎片，Continuous Batching 提升 GPU 利用率，TP 把单卡放不下的模型切到多卡。三件套叠加是工业界标配。

三、TPS 计算

$$\mathrm{TPS} = \tfrac{\mathrm{batch\_size} \times \mathrm{seq\_len}}{\mathrm{decode\_time}} \quad \text{（每 GPU 每秒生成 token 数）}$$

单卡 TPS：用 batch_size、生成总 token 数、解码总时间计算。7B + A100 + batch 32 + seq 1024，TPOT 30ms 时 TPS = 32 × 1024 / (1024 × 0.03) ≈ 1067 tok/s。

$$\mathrm{TPS}_{\text{end2end}} = \tfrac{\mathrm{total\_output\_tokens}}{\mathrm{wall\_clock\_time}} \quad \text{（含 Prefill）}$$

端到端 TPS 还要除以 Prefill 时间和排队时间。生产监控看这个指标更真实。8 卡 A100 + vLLM 部署 70B 模型，端到端 TPS 通常 3000-5000 tok/s。

$$\mathrm{TTFT} \,\text{（首 token 延迟）} \approx \mathrm{Prefill\_time} \approx \mathrm{prompt\_len} \times \mathrm{step\_time}$$

用户感知的"打字机启动"时间。1000 token prompt 在 70B 模型上约 200-500ms。优化方向：Chunked Prefill、FlashAttention、量化。

$$\mathrm{TPOT} \,\text{（每 token 间隔）} \approx \mathrm{decode\_step\_time}$$

用户感知的"打字机速度"。理想 20-30ms/token（流畅），>100ms 用户明显卡顿。受 HBM 带宽限制，模型越大 TPOT 越长。

五、面试 FAQ

Q1：PagedAttention 为什么能省显存？

A：把 KV Cache 分成固定大小页（block 16-128 token），按需分配，类似 OS 虚拟内存分页。传统方式 KV Cache 连续分配（按最大 seq_len 预分配），碎片率 60%+；PagedAttention 复用 block，碎片降到 <5%，batch size 可扩大 4-24x。是 vLLM 论文 SOSP 2023 核心贡献。

Q2：vLLM 和 SGLang 选哪个？

A：通用选 vLLM（成熟稳定，文档全，社区活跃）；复杂 prompt 模板（多轮对话 / 工具调用 / few-shot 长示例）选 SGLang（RadixAttention 前缀复用命中率 30-70%，比 vLLM prefix caching 更激进）。中文场景两者都支持，RAG / Agent 系统优先 SGLang，纯文本生成 vLLM 已足够。

Q3：TP/PP/DP 怎么组合？

A：单机多卡优先 TP（NVLink 快、通信低）；单卡放不下（70B+）用 TP=8 跨机；超大模型（175B+）用 TP=8 + PP=2 跨机；DP 永远可叠加（多副本 + LB）。常见组合：13B 用 TP=1、70B 用 TP=4、175B 用 TP=8 + PP=2、3 副本 DP = 24 卡部署。

Q4：多机推理通信瓶颈？

A：避免跨机 TP（带宽掉到 1/10），跨机用 PP+TP 或纯 DP。硬件上用 NVLink（单机 600GB/s）+ InfiniBand（跨机 200Gbps）+ RoCE 替代 TCP/IP。NCCL 调优：开启 NCCL_IB_HCA、NCCL_SOCKET_IFNAME 绑定网卡，监控 nccl-tests 带宽。

Q5：怎么测 TPS？

A：用 vllm bench serve / genai-benchmark 工具。设置：固定 prompt 长度（如 512）+ 输出长度（如 256）+ 并发数（1/4/16/64），跑 5 分钟取平均值。关键指标：TPS、TPOT、TTFT、显存峰值、GPU 利用率。生产监控加 prometheus_client 实时采集。

Q6：Continuous Batching 怎么实现的？

A：迭代级调度。每生成 1 个 token 后，调度器看是否有新请求在等、是否有请求已完成（碰到 EOS）。完成的请求让出 slot，新请求插入到当前 batch 的空 slot。不再等整批完成才返回，单请求延迟看完成时刻的 P99。实现关键：KV Cache 按请求分块管理（配合 PagedAttention）。

选型决策清单

选 vLLM 的场景

通用文本生成、首次部署推理引擎、文档全社区大、需要稳定 PagedAttention 优化。默认首选，Qwen / Llama / ChatGLM 等主流模型都支持。生产案例丰富。

选 SGLang 的场景

复杂 prompt 模板（多轮 / 工具 / few-shot 长示例占比高）、追求 RadixAttention 前缀复用、Agent / RAG 场景。SGLang 在结构化输出（JSON / grammar）方面也更强。

选 TensorRT-LLM 的场景

NVIDIA 硬件极优化（kernel fusion + INT8/FP8 量化）、追求单卡极限 TPS（比 vLLM 快 1.5-2x）、可接受复杂编译配置（需要先 build engine）。大厂生产首选。

选 LMDeploy 的场景

轻量部署、TurboMind 引擎对国内模型（Qwen / InternLM）优化好、Pythonic API 易集成。中小规模项目首选。
