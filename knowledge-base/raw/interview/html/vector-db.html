向量数据库与数据服务：Pinecone / Weaviate / Milvus / Qdrant / pgvector

2023 以来向量库成为 RAG / 推荐 / 语义搜索的事实标准。从托管 SaaS（Pinecone / Weaviate Cloud）到开源本地（Milvus / Qdrant / Weaviate / Chroma），再到"Postgres + 向量列"（pgvector）和"Redis 加模块"（Redis Stack），10+ 主流方案让"如何选型"成为 LLM 工程师必考点。本页把 10 大向量库、Index / Sharding / Replication 架构、HNSW/IVF/PQ 索引算法、混合检索（BM25+向量）、选型决策、面试 FAQ 一次性串清楚。

一、为什么需要专门的向量库（vs Postgres + 向量列）

  • 规模天花板：Postgres + pgvector 在 1M-10M 向量（1536 维）尚可，100M+ 性能急剧下降，QPS 从 1000 跌到 50
  • ANN 索引缺失：Postgres 原生只有 IVFFlat（暴力），HNSW 要 pgvector 0.5+。专业向量库内置 HNSW / IVF / PQ / Annoy / ScaNN 等
  • 内存压力：Postgres 一次查询要 scan 大量 page，HNSW 全内存。Milvus / Qdrant 把整个索引常驻 RAM（10 亿向量 ≈ 600GB 内存）
  • 混合检索弱：Postgres 全文检索（tsvector）和向量列是两个查询计划，难以联合排序。Qdrant / Elasticsearch 8.x / Vespa 原生混合
  • 分布式能力：Postgres 主从 + Citus 复杂；Milvus / Weaviate 原生分片 / 多副本 / 租户隔离
  • 运维成本：专业向量库自带 backup / scale / monitor；Postgres + pgvector 要自己接 ELK / Prometheus / 备份脚本
  • 代价：① 引入新组件，运维复杂度↑；② 数据一致性（最终一致 vs 强一致）；③ 与业务库 join 不便；④ 收费版（Pinecone / Zilliz）单价高
经验法则：① ≤10w 向量 / 单机 → pgvector 够用（架构简单）；② 10w-1M → Chroma / FAISS（Python 原生、轻量）；③ 1M-100M → Qdrant / Weaviate / Milvus 单机；④ ≥100M → Milvus 分布式 / Pinecone Serverless / Vespa。Postgres 业务表 + 小向量（≤1M）场景最省钱。

四、索引算法对比（HNSW / IVF / PQ / Annoy）

算法原理召回率速度内存适用
HNSW分层 Navigable Small World 图极高（>95%）极快高（10 亿 ≈ 50-100GB）通用首选（生产默认）
IVF（IVFFlat）K-means 聚类，搜索 nprobe 个桶中（80-90%）中低内存紧张 / 牺牲召回
PQ（Product Quantization）向量分段量化压缩中（80-95%）中极低（10x 压缩）海量向量 / 内存受限
IVF-PQ 组合聚类 + 量化中（85-95%）中低亿级以上 / 平衡选择
Annoy（Spotify）随机投影树森林中（85-95%）快（只读）中静态数据集 / 只读场景
ScaNN（Google）各向异性向量量化极高（>95%）极快中Google 内部 / TF 生态

核心思想：Recall@K vs QPS 权衡

QPS = f(M, ef_search, nprobe) ; Recall = g(ef_construction, M, nprobe)

HNSW 调参：① M（每节点连接数，16-64，越大召回↑，内存↑）；② efConstruction（建图深度，100-200，越大建图慢但召回↑）；③ efSearch（搜索深度，50-200，越大 QPS↓但召回↑）。生产默认 M=16, efConstruction=200, efSearch=64。

五、混合检索实现（BM25 + 向量）

# 混合检索：BM25（全文）+ 向量 + Rerank
from qdrant_client import QdrantClient, models
from sentence_transformers import SentenceTransformer, CrossEncoder

# 1. 客户端
client = QdrantClient(url="http://localhost:6333")
encoder = SentenceTransformer("BAAI/bge-m3")  # 1024 维
reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

# 2. 创建带稀疏向量（BM25）的 collection
client.create_collection(
    collection_name="hybrid_docs",
    vectors_config={"dense": models.VectorParams(size=1024, distance=models.Distance.COSINE)},
    sparse_vectors_config={"sparse": models.SparseVectorParams(modifier=models.Modifier.IDF)},
)

# 3. 写入（同时存 dense + sparse）
client.upsert(
    collection_name="hybrid_docs",
    points=[
        models.PointStruct(
            id=i,
            vector={
                "dense": encoder.encode(doc).tolist(),
                "sparse": models.SparseVector(indices=bm25_tokens, values=bm25_weights),
            },
            payload={"text": doc, "category": cat},
        )
        for i, (doc, cat) in enumerate(docs)
    ],
)

# 4. 混合查询（Reciprocal Rank Fusion 融合）
query = "什么是 RAG 检索增强生成？"
query_dense = encoder.encode(query)
query_sparse = bm25_encode(query)

results = client.query_points(
    collection_name="hybrid_docs",
    prefetch=[
        models.Prefetch(query=query_dense, using="dense", limit=20),
        models.Prefetch(query=query_sparse, using="sparse", limit=20),
    ],
    query=models.FusionQuery(fusion=models.Fusion.RRF),  # RRF 自动融合
    limit=10,
)

# 5. Rerank（可选，精度+10%，QPS-30%）
candidates = [r.payload["text"] for r in results.points]
pairs = [(query, c) for c in candidates]
rerank_scores = reranker.predict(pairs)
final = sorted(zip(candidates, rerank_scores), key=lambda x: -x[1])[:5]
混合检索为何必要？① 纯向量擅长语义（"苹果公司" 找到 "iPhone"），不擅长精确关键词（"iPhone 15 Pro Max 256G"）；② 纯 BM25 擅长关键词，不擅长语义。RRF（Reciprocal Rank Fusion）把两者排名倒数相加融合，召回率 +5-15%。Qdrant / Weaviate / Elasticsearch 8.x / Vespa 原生支持。

七、与 LangChain / LlamaIndex 的集成

# LangChain 集成 Qdrant
from langchain_community.vectorstores import Qdrant
from langchain_openai import OpenAIEmbeddings
from langchain.retrievers import EnsembleRetriever
from langchain_community.retrievers import BM25Retriever
from langchain_core.documents import Document

emb = OpenAIEmbeddings(model="text-embedding-3-small")
docs = [Document(page_content=t, metadata={"src": i}) for i, t in enumerate(texts)]

# 1. 向量检索
vdb = Qdrant.from_documents(docs, emb, url="http://localhost:6333",
                            collection_name="lc_demo")
v_retriever = vdb.as_retriever(search_kwargs={"k": 10})

# 2. BM25 检索
bm25_retriever = BM25Retriever.from_documents(docs)
bm25_retriever.k = 10

# 3. 混合（EnsembleRetriever 自动 RRF）
hybrid = EnsembleRetriever(
    retrievers=[v_retriever, bm25_retriever],
    weights=[0.6, 0.4],   # 向量 0.6 + BM25 0.4
)

# 4. 高级 retriever
from langchain.retrievers import (
    ContextualCompressionRetriever,
    MultiQueryRetriever,
    SelfQueryRetriever,
)
from langchain.retrievers.document_compressors import CrossEncoderReranker
from langchain_community.cross_encoders import HuggingFaceCrossEncoder

ce = HuggingFaceCrossEncoder(model_name="BAAI/bge-reranker-base")
compressor = CrossEncoderReranker(model=ce, top_n=5)
rerank_retriever = ContextualCompressionRetriever(
    base_compressor=compressor, base_retriever=hybrid
)

# 5. 检索 + 调用
result = rerank_retriever.invoke("什么是 ReAct Agent？")

十、面试 FAQ

Q1：pgvector 够用吗？

A：场景而定。≤10M 向量 + 业务库强一致 + ≤100 QPS 够用。优势：① Postgres 事务一致、join 方便；② 少组件；③ 已有 Postgres 团队零成本。劣势：100M+ 性能急剧下降、混合检索弱、运维扩展难。生产前必压测。

Q2：Pinecone 贵在哪？

A：① 托管 SaaS 溢价（人 / 时间 / 数据出境成本）；② Serverless 按向量数+查询计费，10M 向量约 $200/月，100M 约 $2000/月；③ 数据锁死在 Pinecone；④ 不可定制。优势：零运维、SLA 99.9%、全球化、低延迟。适合：① 不愿运维；② 全球化业务；③ 项目期初验证。

Q3：Milvus 和 Qdrant 选哪个？

A：Milvus：① 分布式成熟（亿级+生产背书）；② 索引全（HNSW/IVF/PQ/Annoy/GPU）；③ 组件多（etcd + MinIO + Pulsar），运维重。Qdrant：① Rust 性能强（吞吐 +30%）；② 单二进制部署（运维轻）；③ Filter 强大（payload 过滤极快）；④ 文档清晰。中小规模（≤100M）选 Qdrant；超大规模选 Milvus。

Q4：HNSW 和 IVF 区别？

A：HNSW：图索引，全内存，召回率极高（>95%），适合通用首选。IVF：K-means 聚类桶，内存少，速度快，但召回率 80-90%，需 nprobe 调优。生产默认 HNSW；内存紧张或召回要求不高选 IVF / IVF-PQ。ScaNN 是 Google 出的各向异性量化，比 HNSW 召回+速度都优。

Q5：为什么需要混合检索？

A：① 纯向量擅长语义（"苹果公司" → "iPhone"）但不擅长精确关键词（型号、价格）；② 纯 BM25 擅长关键词但不擅长语义。生产 RAG 90% 需要两者融合。RRF（倒数排名融合）或 weighted sum 合并。Qdrant / Weaviate / ES 8 / Vespa 原生支持。实测召回率 +5-15%。

Q6：向量维度怎么选？

A：① OpenAI text-embedding-3-small → 1536 维（默认）；② bge-m3 → 1024 维（中文推荐）；③ bge-large → 1024 维；④ M3E → 768 维；⑤ mxbai-embed-large → 1024 维。维度越大 → 语义越细 → 存储+计算越大。一般 1024 维是性价比最优点。降维：Matryoshka（截断到 256 维仍可用）。

Q7：向量库如何选 metadata 过滤？

A：① payload 索引（Qdrant / Milvus 都建在向量字段旁）；② 标量字段先 filter 再 search（pre-filter）；③ 复杂 query 走 query plan（Milvus 表达式 / Qdrant filter）。生产 90% 用 pre-filter（先按 category=tech 过滤再向量检索）。Qdrant filter 极快（payload 全内存）。

Q8：怎么保证数据一致性？

A：① 强一致（pgvector / Redis）→ 事务内写入；② 最终一致（Milvus / Pinecone）→ 写入后 1-5s 可查；③ 生产中常用方案：业务库事务 + 异步向量写入（消息队列） + 失败重试。Qdrant 支持 Write-Ahead-Log + Snapshot。Milvus 支持 Exactly-Once 语义。RAG 场景 90% 用最终一致即可。

Q9：如何监控向量库？

A：① Prometheus + Grafana（Qdrant / Milvus 原生 exporter）；② 关键指标：QPS / P50/P99 延迟 / 召回率（业务侧 A/B 测）/ 索引大小 / 内存使用 / 副本滞后；③ 日志：query latency 分布、错误率、Top K 命中率；④ 告警：P99 > 100ms、QPS 跌 30%、副本切换、索引损坏。生产中每条查询要打 trace。

Q10：Rerank 一定要吗？

A：不一定。简单场景：向量 Top-5 即可，Rerank +10% 精度但 -30% QPS。复杂场景：① 多语种/长文档 → 必加；② 对召回率敏感（医疗/法律）→ 必加；③ 高 QPS（>100）→ 慎用。常见组合：向量 Top-50 → Rerank → Top-5 给 LLM。bge-reranker / Cohere Rerank / Jina Rerank 是主流。
