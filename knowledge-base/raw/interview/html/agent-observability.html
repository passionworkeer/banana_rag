Agent 可观测性：让 Agent 系统的"黑盒"变"白盒"

传统软件靠日志 / 指标 / Trace 三大支柱做可观测性。Agent 系统需要"第 4 个支柱"——LLM Trace：消息流、Token 成本、Tool 调用、决策路径、Eval 分数。LangSmith / Langfuse / Helicone 是主流平台。本页讲清 Trace 数据结构、Eval 集成、生产级监控指标。

二、为什么 Agent 需要专门的 Trace

  • 非确定性：同样输入可能走不同路径，传统日志不够
  • 多步：一个任务 N 步，调试要还原"哪步错了"
  • 成本敏感：LLM 按 token 计费，需要看到底哪步贵
  • 质量难评估：输出对不对需要 LLM-as-Judge 评分
  • 幻觉：需要看 prompt / retrieval / 工具结果，定位幻觉来源

五、OpenTelemetry + GenAI 语义

  • OpenTelemetry：CNCF 标准的 Trace 协议（opentelemetry.io）
  • OTLP：trace / metrics / logs 通用传输协议
  • OpenLLMetry：在 OTel 上加 LLM 专属 span 类型（prompt / completion / token usage）
  • 优势：和 Jaeger / Tempo / Datadog 等通用 trace 平台兼容
  • 劣势：LLM 专用语义还在演进，比 LangSmith 弱
Langfuse / Helicone 都支持 OpenLLMetry——选 OpenLLMetry 不会"被厂商绑死"。

六、Eval 集成 3 模式

  • 在线 Eval：每次 Run 完成后跑 LLM-as-Judge，记录分数
  • 离线 Eval：从 Trace 库采样、跑评估集、回归对比
  • 用户反馈：👍 / 👎 / 文字反馈回流到 Trace 关联
生产中"在线 Eval + 用户反馈"双轨是金标准——前者自动化覆盖广、后者信号真实。

七、面试 FAQ

Q1：Agent 可观测性为什么比传统可观测性复杂？

A：3 个差异：① 非确定性（同样输入可能走不同路径）；② 多步（一个任务 N 步 trace 嵌套）；③ 质量难评（输出对不对需要 LLM-as-Judge）。传统 Logs/Metrics/Traces 三大支柱不够，需要 LLM Trace（第 4 支柱）+ 评估体系。

Q2：LangSmith / Langfuse / Helicone 选哪个？

A：① LangChain 生态深度用 LangSmith；② 自托管 / 框架无关 / 开源用 Langfuse；③ 简单 OpenAI 代理 / 成本优先用 Helicone。三者核心能力（trace + cost + eval）有重叠，关键是部署方式和生态契合度。

Q3：Agent Trace 最该看什么？

A：3 个核心：① 哪步耗时最长（找瓶颈）；② 哪步成本最高（找优化点）；③ 哪步 LLM-as-Judge 分数低（找质量短板）。其次看 Tool 失败率、Replan 次数、消息 token 长度。

Q4：怎么用 Trace 调试 Agent 失败？

A：4 步：① 找到失败 Run；② 看 LLM 评分低的 message；③ 检查 prompt / completion（看是否理解错）；④ 看 Tool 调用结果（看是否拿错数据）。LangSmith 的一键回放 + 时间轴最直观。

Q5：Trace 数据要不要存？存多久？

A：存，但要分层：① 完整 prompt / completion 存 7-30 天（合规 + 容量）；② 元数据（token / cost / score）永久存（用于分析）；③ 敏感数据要脱敏（手机号 / 邮箱 / 身份证）。生产中 PII 检测是 Trace 平台的标配功能。

Q6：OpenLLMetry 和 LangSmith 谁更标准？

A：OpenLLMetry 基于 OTel 标准、跨厂商；LangSmith 是 LangChain 私有实现。前者更"开放"、不会绑死；后者功能更完善、上手快。生产中"LangSmith 调试 + OpenLLMetry 上报"双链路是常见组合。

Q7：怎么把 Trace 接到 Grafana / Datadog？

A：OpenLLMetry 把 LLM 事件转成 OTel span，通过 OTLP 协议发给 Grafana Tempo / Datadog APM。需要：① OpenLLMetry SDK 集成；② OTel Collector；③ Grafana / Datadog 配置 OTLP endpoint。Langfuse / Helicone 也支持这种导出。

Q8：Agent Eval 和传统单元测试区别？

A：3 个差异：① 输入分布（Eval 集是抽样代表性 / 单元测试是边界覆盖）；② 期望输出（Eval 是模糊"好"/"坏"、单元测试是精确断言）；③ 执行频率（Eval 持续跑 / 单元测试每次 CI）。Eval 体系是 Agent 系统的"持续质量门"。

八、回答模板与加分项

30 秒电梯版

Agent 可观测性 = LLM Trace（第 4 支柱）+ Eval 集成。平台：LangSmith（LangChain 一等公民）/ Langfuse（开源 + 框架无关）/ Helicone（OpenAI 代理）。关键指标：质量（完成率 / 幻觉率）、成本（token / 单日预算）、延迟（P95）、错误（Tool 失败率）。OpenLLMetry 基于 OTel 是开放标准。

5 分钟深入版

从动机（Agent 黑盒难调）→ Trace 数据结构（Run / Message / LLM Call / Tool Call / Eval）→ 3 大平台对比 → 4 类关键指标 → OpenLLMetry 标准 → Eval 集成 3 模式（在线 / 离线 / 用户反馈）→ 调试 4 步法 → 数据保留与脱敏。能讲清"为什么 LLM Trace 是第 4 支柱"、"为什么 OpenLLMetry 不绑死"，立刻显得懂生产 Agent 工程。

加分：项目案例

讲一次"用 Trace 调试 Agent 失败"——比如客服 Agent 失败率突涨，LangSmith 看到"Tool 失败率从 2% 涨到 15%"，定位到第三方 API 限流；加 retry + 缓存后恢复。讲排查过程立刻显得有真经验。

加分：知道局限

Agent 可观测性不是银弹：① Trace 本身有成本（存储 + 索引）；② 敏感数据脱敏难（prompt 里混着 PII）；③ LLM-as-Judge 评估本身有偏差；④ 跨 vendor 切换成本。诚实说"可观测性是 Agent 上线前提，不是上线后补救"得分更高。
