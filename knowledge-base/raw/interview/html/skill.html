Skill 机制

Skill 创建方式（NL / 代码 / hybrid）、与 MCP/Tool 的区别与组合。

SkillMCPToolHybridReusable

一、Skill 是什么

  • Skill 定义：可复用的能力单元，封装提示词 + 工具调用 + 工作流
    • 形式：YAML / Markdown / Python 描述的能力包
    • 本质：让 LLM 学会"在某个场景下该怎么做"
    • 代表：Anthropic Skills、Cursor Skills、Codex Skills、Claude Code Skills
  • 三种创建方式：
    • NL 描述（自然语言）：用 Markdown 写 Skill 行为（如"你是一名代码评审专家，看到 PR 时检查 X、Y、Z"），模型读 description 学会调用方式
    • 代码实现（Code）：用 Python / JS 写 Skill（如 Cursor .cursor/skills/ 目录），含具体逻辑和工具
    • Hybrid（混合）：NL 描述意图 + 代码工具实现（如"评审代码" Skill 包含 git diff 工具 + LLM 评审 prompt）
  • 与 Tool 区别：
    • Tool：单次函数调用（调一下得到结果），原子能力
    • Skill：多步工作流（组合多个 Tool + 决策逻辑），复合能力
    • 类比：Tool 是函数，Skill 是 SDK / 包
  • 与 MCP 区别：
    • MCP：协议层（如何传输、发现、管理工具）
    • Skill：内容层（如何编排工具、设计工作流）
    • Skill 内部可调用 MCP Tool（如"商品推荐 Skill"内部用 MCP 调 search_products）
  • 组合关系：Skill → 编排多个 Tool（含 MCP Tool）→ 完成任务
  • 工程实践：
    • Skill 版本管理（Git 追踪 + 语义化版本）
    • 依赖管理（Skill 依赖的 Tool / Prompt / 模型版本）
    • 测试（单元 + 端到端 + 人工 review）
    • Skill 市场 / 共享库（团队内复用）

实战经验：Tool 设计要"小而专"（一个函数做一件事），Skill 设计要"大而完整"（解决一类问题），Agent 设计要"灵活可组合"（按需选 Skill）。三层职责清晰，团队规模化复用。

二、Skill 调用链

Skill 调度器先按用户意图匹配 Skill（"评审 PR" → code-review Skill），Skill 内部用 LLM 决定下一步调哪个 Tool（git_diff / llm_review / comment_pr），最后通过 MCP 协议调用业务系统。三层解耦：调度器（路由）、Skill（编排）、Tool（执行）。

三、Skill 定义示例

Skill YAML 定义（Anthropic Skills 规范）

name: code-review
version: 1.2.0
description: |
  评审代码 PR，检查代码风格、潜在 bug、安全问题。
  当用户说"评审"、"review"、"检查代码"时触发。
trigger:
  keywords: ["评审", "review", "检查代码"]
  embedding_match: true
steps:
  - id: get_diff
    tool: git_diff
    params: { base: "main" }
  - id: llm_review
    tool: llm_review
    params: { prompt: "评审以下 diff..." }
  - id: post_comment
    tool: comment_pr
    params: { body: "{{llm_review.result}}" }
tools:
  - git_diff
  - llm_review
  - comment_pr
tests:
  - fixture: pr_with_bug.json
    expect: contains("potential null pointer")
versioning:
  strategy: semver
  changelog: CHANGELOG.md

关键字段：name + description（调度器匹配用）、trigger（何时激活）、steps（工作流）、tools（依赖声明）、tests（回归测试）、versioning（版本管理）。

三、消息格式

Request（Client → Server）

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search_products",
    "arguments": { "keyword": "袜子" }
  }
}

Response（Server → Client）

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": { "items": [...] }
}

Error（参数缺失 / 工具不存在）

{
  "jsonrpc": "2.0",
  "id": 1,
  "error": { "code": -32602, "message": "keyword is required" }
}

Notification（Server 主动推送，无需回复）

{
  "jsonrpc": "2.0",
  "method": "notifications/resources/updated",
  "params": { "uri": "file:///orders/2026-06-03.json" }
}

五、面试 FAQ

Q1：Skill 和 Tool 区别？

A：Tool 是单次函数调用（调一下得到结果，原子能力），Skill 是多步工作流（组合多个 Tool + 决策逻辑 + 状态，复合能力）。类比：Tool 是函数，Skill 是 SDK / 包。Tool 必须显式调用，Skill 可触发式激活（按 NL 描述自动匹配）。

Q2：Skill 和 MCP 关系？

A：MCP 是协议层（如何发现、传输、管理工具，跨厂商标准），Skill 是内容层（如何编排工具、解决什么问题，应用设计）。Skill 内部可调用 MCP Tool 完成任务。两者正交：MCP 管"怎么调"，Skill 管"调什么、按什么顺序"。

Q3：怎么创建第一个 Skill？

A：五步法：① 明确场景（解决什么问题，谁用）；② 写 NL description（让模型理解何时调用）；③ 列 Tool 依赖（需要哪些工具）；④ 设计工作流（步骤 + 决策 + 异常处理）；⑤ 写测试用例 + 跑端到端验证。从最痛的 1 个场景切入，跑通后再扩展。

Q4：Skill 怎么测试？

A：三层测试。① 单元测试（每个 step 独立验证，调 mock Tool）；② 端到端测试（用真实 fixture 跑全流程，对比 expected output）；③ 人工 review（关键 Skill 抽样人工评，统计准确率 / 满意度）。CI 集成 Skill 测试，每次提交自动回归。生产环境加 trace_id 全链路可观测。

Q5：Skill 怎么版本管理？

A：跟代码一样用 Git + 语义化版本（v1.2.0）。每次重大变更 bump major，向后兼容 bump minor，修补 bump minor。Skill 文件加 version 字段 + CHANGELOG.md。升级流程：先在测试 Skill Router 上线，观察 1 周没问题再升正式。允许 Skill 多版本并存（老用户跑老版本）。

Q6：Skill 和 Prompt 区别？

A：Prompt 是单次输入（一次性给模型的指令，文本级别），Skill 是可复用的多步能力（包含 Prompt + Tool + 工作流 + 测试，包级别）。Prompt 是 LLM 时代的"配置"，Skill 是 Agent 时代的"插件"。Prompt 改了就丢，Skill 有版本、可回滚、可共享。

选型决策清单

选 NL 描述 Skill

Skill 主要是 LLM 决策 + 文本生成（"代码评审"、"PRD 写作"、"客服话术"）。开发快、可读性高、模型能自适应。Anthropic Skills 推荐方式。

选 Code 实现 Skill

Skill 含复杂逻辑 / 状态机 / 精确控制（"CI/CD 流水线"、"数据 ETL"、"部署脚本"）。需要确定性行为、需 unit test。Cursor / Codex Skills 偏这种方式。

选 Hybrid Skill

Skill 同时含 LLM 决策 + 精确执行（"调研报告生成"：LLM 决定查什么 + 调 API 查数据 + LLM 写报告）。最灵活也最复杂，企业内最常见。

不引入 Skill 的场景

Tool 数量少（<5）、场景单一、团队规模小（<3 人）。直接用 Prompt + Tool 即可，过度设计反而拖慢迭代。Skill 适合"问题重复度高、调用频次高、需跨人复用"的场景。
