Context Engineering：Prompt Engineering 的"上半场"

Anthropic 2025 提出的概念：把所有"模型决策时能看到的信息"——system prompt、few-shot、RAG 检索、工具结果、长期记忆——都视为可设计的"上下文工程"。比 Prompt Engineering 视角更宽：解决"为什么模型在长对话中忘记约束"、"为什么 RAG 检索回来反而干扰"等问题。

一、Prompt Engineering vs Context Engineering

二、Context Engineering 4 大组成

  • Instructions：system prompt + user prompt（角色 / 任务 / 约束）
  • Knowledge：RAG 检索、长期记忆、文档引用
  • Tools：可用工具的定义、tool 输出回填
  • Examples：few-shot 示例、之前成功 / 失败的样本
Anthropic 原话："Context Engineering 是精心策划的、刚好够用、刚好及时的信息集合，让 LLM 完成任务。"

三、Just-in-Time Context

  • 静态 Context：把"所有可能用到的信息"塞 system prompt（贵 + 易超长）
  • JIT Context：按需动态检索 / 加载（省 token + 更准）
  • 类比：传统软件把所有依赖打进二进制 vs 按需 npm install
Agent 系统几乎都是 JIT：RAG 按 query 检索、Tools 按需调用、Memory 按需 retrieve。

四、Context Engineering 设计 5 原则

原则含义反例
Just Enough给"刚好够用"的信息，不多不少把所有工具描述塞 prompt
Just-in-Time按需动态加载每次 system prompt 全量
Structured结构化（JSON / Schema）让模型易解析纯自然语言大段文字
Attributed每条信息标来源（用于"如果 X 不可信"）把检索结果当事实
LifecycleContext 也有生命周期（生成 / 维护 / 失效）Memory 永远不被更新

五、Context 常见失败模式

  • Context Poisoning：检索回幻觉 / 错误信息，污染后续推理
  • Context Distraction：context 太多反而分散注意力
  • Context Confusion：不同 context 块（如 system vs user）冲突，模型不知道听谁
  • Context Clash：工具结果和 system prompt 矛盾
  • Context Forgetting：长对话中 system prompt 约束被"挤掉"（attention 集中在最新 token）

六、Context Engineering 与 RAG 关系

RAG 是 Context Engineering 的一个子集——负责"知识"这一维度。但 Context Engineering 更宽：

  • Prompt：instruction context
  • RAG：knowledge context
  • Tool：actionable context（让模型能"做"）
  • Memory：historical context（让模型记得过去）
  • Examples：demonstrative context（让模型会做）
判断口诀：单一对话用 Prompt Engineering；多步 / 多工具 / 多 session 用 Context Engineering。

七、面试 FAQ

Q1：Context Engineering 和 Prompt Engineering 区别？

A：Prompt Engineering 关注"用户那一句话和 system prompt"；Context Engineering 关注"模型决策时能看到的全部信息"——包括 RAG 检索结果、工具输出、长期记忆、few-shot 示例。Context Engineering 是更宽的视角，承认"提示词只是 context 的一部分"。

Q2：Context Engineering 适合什么场景？

A：① Agent 系统（多步 + 多工具 + 多 session）；② 复杂 RAG（多次检索、多源融合）；③ 长对话助手（需维护 user preference）；④ 多用户个性化（每个用户有独立 context）。简单单轮对话用 Prompt Engineering 足矣。

Q3：Context 越丰富越好吗？

A：不一定。"Lost in the Middle" + Context Distraction 都说明：context 多了反而干扰。原则是"just enough, just in time"——只给当前任务真正需要的信息，按需加载。Anthropic 建议"为模型做减法"。

Q4：Context Engineering 怎么评估？

A：3 层：① 任务完成率（context 是否含必要信息）；② Token 成本（context 是否精炼）；③ 失败模式（Context Poisoning / Confusion 频率）。可建评估集对比"加 context 前 vs 后"差异。

Q5：Context 顺序有讲究吗？

A：有。"Lost in the Middle"显示：放在头尾的 context 关注度高、中间低。所以关键约束（system prompt 核心规则）放头、关键事实放尾、中间放"参考但不关键"。Claude / GPT 都有"position bias"。

Q6：Context Engineering vs Memory 关系？

A：Memory 是 Context Engineering 的一部分——历史 context。但 Memory 有"持久化"特征（跨 session），其他 context 多为"一次性"（当前 session）。生产中 Memory 需要定期去重、过期、合并。

Q7：RAG 检索结果会污染 context 吗？

A：会。Context Poisoning 是 RAG 系统的最大风险——检索回错误 / 旧 / 矛盾信息，模型会"信以为真"。解法：① 标 attribution（这条信息来自 X）；② 多源交叉验证；③ 检索评分低于阈值的丢弃。

Q8：Context Engineering 有现成框架吗？

A：没有"Context Engineering 框架"这种统一抽象，但 LangChain / LlamaIndex 在 prompt 模板 + RAG + Memory 层面的设计就是 Context Engineering 实践。Anthropic 提供"Contextual Retrieval"（检索结果额外用 LLM 加 context 后再 embedding）的具体方案。

八、回答模板与加分项

30 秒电梯版

Context Engineering 是 Anthropic 2025 提出的"Prompt Engineering 升级版"——把模型决策时能看到的全部信息（system + RAG + tools + memory + few-shot）视为可设计的"上下文工程"。5 原则：Just Enough / Just-in-Time / Structured / Attributed / Lifecycle。常见失败：Poisoning / Distraction / Confusion / Forgetting。

5 分钟深入版

从动机（Prompt Engineering 不够用）→ 4 大组成（Instructions / Knowledge / Tools / Examples）→ Just-in-Time vs 静态 → 5 设计原则 → 5 失败模式 → 与 RAG / Memory 关系 → 与 Prompt Engineering 边界。能讲清"为什么 Just-in-Time 比全量塞入好"、"为什么 Context 顺序有讲究"，立刻显得跟得上 2025 趋势。

加分：项目案例

讲一次"从 Prompt Engineering 升级到 Context Engineering"——比如客服 Agent 早期 system prompt 100 行（含全部工具说明 + 全部 FAQ），token 贵、模型"分心"；改 Context Engineering 后 system prompt 30 行 + 工具按需加载 + RAG 检索 FAQ，单次成本 -50%，完成率 +15%。

加分：知道局限

Context Engineering 不是银弹：① 多了仍会 "Lost in the Middle"；② Context Poisoning 难完全防；③ 评估难（context 维度太多）；④ 不适合单轮简单任务。诚实说"Context Engineering 是 Agent 时代的系统设计视角，不是 prompt 技巧"得分更高。
