Rerank 重排序

用 Cross-Encoder / ColBERT / LLM 对初筛结果精排，提升 Top-K 准确率。

Cross-EncoderColBERTLLM RerankTop-KMRR

一、为什么需要 Rerank

  • Embedding 召回的局限：双塔结构 query 与 doc 无 token 级交互，召回快但精度有限
    • Bi-Encoder 独立编码 q 和 d，最后只算向量相似度
    • 无法捕捉"词序否定 / 同义改写 / 上下文依赖"等细粒度语义
    • Top-100 召回里常混入"语义相近但答案无关"的文档
  • Rerank 价值：用更"重"的模型对召回 Top-100 精排，输出 Top-10 给下游
    • 性能与精度的折中：召回要快、要召回率；Rerank 要准、要精排
    • 两阶段架构（Recall + Rerank）是工业界 RAG 标配
  • 三种主流方案：
    • Cross-Encoder：q + d 拼接过 BERT，输出相关性分数 — 准但慢
    • ColBERT：late interaction，token 级相似度聚合 — 平衡精度与速度
    • LLM Rerank：用 LLM 评估相关性（GPT-4 / Qwen-Long）— 最准但最贵
  • 评估指标：MRR（平均倒数排名）、NDCG@K（归一化折损累计增益）、Recall@K、MAP
  • 工程权衡：
    • Cross-Encoder：单次 ~50ms，Top-100 全打分 ~5s，中文场景首选 bge-reranker-v2-m3
    • ColBERT：单次 ~5ms，可处理 Top-1000，索引大但查询快
    • LLM Rerank：单次 ~500ms-2s，Top-50 内精选时使用
方案精度速度成本适用规模代表实现
Bi-Encoder（召回）中极快低百万级BGE / M3E / OpenAI Embedding
Cross-Encoder高慢中Top-100 内bge-reranker、cohere-rerank

Rerank vs Recall 职责分工

维度Recall（召回）Rerank（精排）
目标召回率优先 — 不漏掉正确答案精度优先 — Top-K 必须准
候选数百万 / 千万级文档Top-100 / 200 候选
模型Bi-Encoder（独立编码）Cross-Encoder（联合编码）
速度极快（向量检索毫秒级）较慢（每对 q-d 都要过模型）

实战经验：先做召回（R@100 拉到 90%+），再上 Rerank（NDCG@10 提升 10-20%）。如果 R@100 就低，说明 Embedding 选型或文档处理有问题，不应先加 Rerank。

二、Rerank 流程

两阶段流水线：Embedding 召回解决"找得到"问题，Cross-Encoder 精排解决"找得准"问题。最终 Top-10 作为 RAG 的 context 喂给 LLM。

三、Cross-Encoder 公式

$$\mathrm{score}(q, d) = W \cdot s(\mathrm{[CLS]}_{[q;d]})$$

含义：q 和 d 拼接为 [CLS] q tokens [SEP] d tokens [SEP] 一起过 BERT，取 [CLS] 位置的隐藏向量 s，再过线性层 W 得到相关性分数。

$$P(\text{relevant}) = \sigma(\mathrm{score}(q, d)) = \sigma(W \cdot s_{\mathrm{[CLS]}} + b)$$

实际实现里通常用 sigmoid 归一化到 (0, 1)，方便按阈值过滤或直接作为相关度分数排序。

$$\mathrm{Loss} = -\log P(d^{+} > d^{-} \mid q)$$

训练用 pairwise ranking loss：让正样本分数高于负样本，对比损失。典型代表：sentence-transformers 的 CrossEncoder 类。

ColBERT Late Interaction

$$S(q, d) = \sum_{i \in q}\, \max_{j \in d}\, E(q_{i}) \cdot E(d_{j})$$

含义：每个 query token 找到 doc 中最相似的 token（max-pool），再对所有 query token 求和。保留了 token 级交互，但 doc 端向量可预计算。

$$\text{索引大小} \approx \sum_{d \in D} |d| \times \mathrm{dim}$$

代价是索引大（每个 token 都要存向量），查询时只用算 query 端向量 + 做 max-pool，比 Cross-Encoder 快一个数量级。

$$S(q, d) = \sum_{i}\, \max_{j}\, \tfrac{E(q_{i}) \cdot E(d_{j})}{\|E(q_{i})\| \cdot \|E(d_{j})\|}$$

实际实现用 cosine 相似度 + 归一化，配合 PLAID 索引做近似加速。

五、面试 FAQ

Q1：Rerank 为什么不能替代召回？

A：召回要快、要召回率（宁可多不能漏），Rerank 要准、要精排（输出 Top-K 必须对）。两者职责不同：Cross-Encoder 对百万级文档全打分要十几分钟，Bi-Encoder 向量检索只要 10ms。生产必须两阶段：召回解决"找得到"，Rerank 解决"找得准"。

Q2：Cross-Encoder 慢在哪？

A：每个 query-doc 对都要过一遍完整 BERT。100 个候选 = 100 次 BERT 前向，单次 ~50ms 就是 5 秒。无法预计算（q 和 d 拼接才生效），无法并行到 GPU batch 之外。优化方向：候选数限制 Top-100 / 200，或换 ColBERT 平衡。

Q3：ColBERT 怎么平衡精度和速度？

A：离线算 doc 端 token 向量（一次性，可并行），存到 PLAID 索引；在线只算 query 端 ~20 个 token 向量，然后和 doc 端做 max-pool 相似度。查询延迟 ~5ms，是 Cross-Encoder 的 1/1000，精度接近。代价是索引大（每个 token 都要存 128 维向量）。

Q4：LLM Rerank 怎么降本？

A：三个手段：① 限制候选数（Top-50 内精选，gpt-4 一次 50 个打分 ~$0.05）；② 缓存 LLM 评分结果（q-d 哈希作 key，命中复用）；③ 用小模型 LLM（如 Qwen2.5-7B）替代 GPT-4，本地部署零边际成本。常见做法是 Cross-Encoder 先粗排到 10-20，再 LLM 精排。

Q5：Rerank 怎么评估？

A：自动指标（MRR / NDCG@K / Recall@K）+ 人工评估（标注 query-doc 相关性 0/1/2）+ 端到端评估（RAG 答案质量是否提升）。生产中常用 A/B 测试对比上线前后用户满意度。指标要兼顾离线评估集和在线 A/B 真实反馈。

Q6：Top-K 设多大合适？

A：看下游消费。生成模型（RAG）看 Top-5/10（context 窗口有限、过长会引入噪声）；搜索展示看 Top-20（用户浏览多页）；评估指标看 NDCG@10（业界标准）。Top-K 太大会引入噪声，Top-K 太小会漏掉正确答案。一般 Recall@100 ≥ 90% 是召回阶段的合理目标。

选型决策清单

选 Cross-Encoder 的场景

召回数 ≤ 200、对精度要求高、可接受秒级延迟、中文场景（bge-reranker-v2-m3、cohere-rerank-3）。最常见选型，工业界默认方案。

选 ColBERT 的场景

召回数 1000+、需要毫秒级延迟、索引磁盘可承受（GB 级）、英文为主（ColBERTv2 / PLAID）。学术和高性能场景优选。

选 LLM Rerank 的场景

候选 ≤ 50、追求最高精度、已有 LLM 推理能力、愿意付 token 成本（GPT-4 / Qwen-Long 打分）。适合关键路径（如法律 / 医疗检索）。

不引入 Rerank 的场景

召回 Top-10 就能命中正确答案（Recall@10 > 95%）；延迟极敏感（如实时聊天 200ms 内）；候选文档全相关（数据源干净）。过度工程反而拖慢系统。
