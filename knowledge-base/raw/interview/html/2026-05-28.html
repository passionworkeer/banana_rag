一、RAG vs 规则系统：何时选哪个？

这是面试最常考的设计题。核心判断依据是「知识的确定性」和「知识的变化频率」。

🔍

RAG 适用场景

知识分散、更新频繁、边界模糊、语义理解需求高

  • 政策文件、产品手册（需要理解语义）
  • 实时数据（股价、库存、天气）
  • 跨知识库检索（多文档综合）
📏

规则系统适用场景

知识确定、边界清晰、零容忍错误、不允许幻觉

  • 合规校验（法律/财务/安全）
  • 业务流程（审批流、工单处理）
  • 确定性计算（税务/利息/折扣）
🔀

混合架构（最优解）

规则兜底 + RAG 增强，两者协同

  • RAG 提供知识背景和参考
  • 规则系统做最终决策验证
  • 规则优先，RAG 补充

"没有最好的方案，只有最合适的方案。规则系统是保险，RAG 是智囊。合规场景下保险先行，智囊辅助；探索场景下智囊为主，保险兜底。"

三、Embedding 检索实践

Embedding 是 RAG 的核心，质量直接决定召回效果。

Embedding 模型 维度 适用场景 特点
text-embedding-ada-002 1536 通用场景 OpenAI 官方，通用强
text-embedding-3-small/large 256~3072 成本敏感场景 价格低，维度可压缩
BGE-large-zh 1024 中文专业场景 中文能力最强，开源免费
M3E 1024/2048 中文Embedding MokaNN 开源，中文效果好
NV-Embed-QA 4096 复杂问答 NVIDIA 最新，QA 任务优化

Embedding 调优三板斧

1. 领域适配：使用领域数据微调 Embedding 模型（如用医疗数据训练医疗 Embedding）
2. 多路召回：BM25 + 向量 + 关键词，三路召回取并集
3. Rerank：用交叉编码器做二次排序（如 Cohere Rerank）

四、知识过期治理四步法
1

版本标签管理

每个 Chunk 带元数据：version、last_updated、source、confidence。检索时过滤过期版本（version < 最新version - 阈值）。

2

增量索引 + 全量回源

数据变更时，只索引变化的文档，而非全量重建。使用软删除（is_deleted 标记）而非硬删除，保留审计记录。

3

时效性感知检索

根据 query 判断时效性：政策类强依赖最新版本，价格类时效性中等，知识类容忍历史版本。检索时按时效性调整 score 权重。

4

置信度校准

RAG 返回结果时附带置信度分数：高分结果直接用，低分结果触发人工复核或规则兜底。避免低置信度结果误导模型。

五、上下文裁剪策略

当召回的 Chunk 超出模型上下文限制时，需要裁剪。常见三种策略：

🔪 硬截断

  • 直接按 token 数量截断
  • 简单但粗暴，可能截断关键信息
  • 适合：内容重要性均匀分布的场景

🗜️ 软压缩

  • 用小模型做摘要压缩
  • 保留关键实体和结论
  • 适合：长文档的关键信息提取

Recurrent Chunking（递归切片）

先用粗糙切片 → 评估每块的信息熵 → 信息密度低的块继续细分 → 直到每块信息熵超过阈值。这是 MinerU 等专业文档解析工具的核心思路。

产品经理视角

知识库治理决定 Agent 回答的准确性和可信度，直接影响用户留存和产品口碑。

核心价值

知识库质量 = 回答准确率 = 用户信任度 = 产品留存率。知识库治理差的典型表现：用户问一个具体问题，Agent 给出"根据相关文件显示"的回答，但说的内容是错的或过时的。

PRD 中必须定义的内容

  • 知识库的来源和更新频率（谁来维护？多久同步一次？）
  • 回答的置信度策略（不确定时是"我不知道"还是"猜一个"？）
  • 降级路径（知识库查不到时是规则兜底还是直接拒答？）
  • 准确性验收标准（知识密集型问题准确率 > 90%）

竞品分析：知识库治理能力对比

  • Notion AI：实时索引 Notion 内容，知识库与笔记同步强
  • Copilot：规则系统保障代码安全，RAG 提供上下文
  • Perplexity：实时 RAG 搜索，但有时效性幻觉问题
  • 火鹰合规：RAG + 规则双重校验，合规场景下必须零容忍错误

成功指标定义

  • 知识检索召回率（Relevant Chunk 出现在 Top-5 的比例）> 85%
  • RAG 回答准确率 > 90%（人工评测）
  • 知识过期投诉率 < 2%
  • 上下文截断导致的答案不完整率 < 5%
技术开发视角

多路召回 + Rerank 实战代码

rag_pipeline.py - 多路召回 + Rerank
class HybridRetriever: def retrieve(self, query: str, top_k: int = 20) -> List[Document]: """ 三路召回：向量 + BM25 + 关键词 最终用 Rerank 排序 """ # 1. 向量召回 vector_results = self.vector_db.search(query, top_k=50) # 2. BM25 召回 bm25_results = self.bm25_index.search(query, top_k=50) # 3. 关键词召回 keyword_results = self.keyword_index.search(query, top_k=30) # 4. RRRF 融合排序 fused = rrrf_fusion([vector_results, bm25_results, keyword_results]) # 5. Rerank 二次排序 reranked = self.reranker.rerank(query, fused[:100], top=top_k) return reranked def rrrf_fusion(results_list: List[List]) -> List: """Reciprocal Rank Fusion：简单高效的融合算法""" scores = {} for results in results_list: for rank, doc in enumerate(results): doc_id = doc.id scores[doc_id] = scores.get(doc_id, 0) + 1 / (60 + rank + 1) return sorted(scores.items(), key=lambda x: x[1], reverse=True)

知识过期管理：版本感知的 Chunk

chunk_manager.py - 版本标签与过期检测
class VersionedChunk: version: str # v1.0, v2.1 last_updated: datetime source: str # 文件名、URL is_deleted: bool = False # 软删除标记 confidence: float # 置信度 0~1 def retrieve_with_freshness(query: str, top_k: int, max_age_days: int = 30): results = vector_db.search(query, top_k=100) fresh_results = [] for chunk in results: age = (now - chunk.last_updated).days if age > max_age_days and chunk.confidence < 0.7: # 过期且置信度低：标记为可能过期 chunk.metadata["warning"] = "知识可能已过期" fresh_results.append(chunk) return fresh_results[:top_k]

上下文裁剪：LLMMapReduce 摘要压缩

context_compression.py - 智能裁剪
class ContextCompressor: def compress(self, chunks: List[Document], max_tokens: int): """MapReduce 风格上下文压缩""" # Step 1: Map - 每个 Chunk 生成摘要 summaries = [self.summarizer.summarize(c) for c in chunks] # Step 2: 检查总 token 是否超限 total = count_tokens(summaries) if total <= max_tokens: return summaries # Step 3: Reduce - 合并摘要再压缩 merged = "\n".join(summaries) while count_tokens(merged) > max_tokens: merged = self.summarizer.summarize(merged) return [merged] def smart_truncate(chunks: List[Document], max_tokens: int): """按信息密度排序，优先保留高密度块""" for chunk in chunks: chunk.metadata["density"] = compute_density(chunk.text) chunks.sort(key=lambda c: c.metadata["density"], reverse=True) result, total = [], 0 for c in chunks: chunk_tokens = count_tokens(c.text) if total + chunk_tokens > max_tokens: break result.append(c) total += chunk_tokens return result

面试题 & 参考答案
1
什么时候用 RAG，什么时候用规则系统？

判断维度：知识确定性 + 变化频率 + 零容忍度

  • 规则系统：确定性高、边界清晰、不允许错误（合规校验、审批流、计算公式）
  • RAG：知识分散、更新频繁、需要语义理解（政策文件、产品手册、实时数据）
  • 最优解：混合架构。规则做决策验证，RAG 做知识补充
2
Embedding 召回效果差怎么排查和优化？

排查方向：模型匹配度 → 向量质量 → 切片策略 → 融合方式

  • 模型不匹配：通用 Embedding 在专业领域效果差，换用领域微调模型（BGE-large-zh for Chinese）
  • 切片质量差：按语义单元切片（句子/段落），避免在句子中间截断，块大小 256~512 tokens
  • 单路召回不足：多路召回（向量 + BM25 + 关键词）用 RRF 融合
  • 排序效果差：加一层 Rerank（Cross-Encoder 或 Cohere Rerank）做二次排序
3
知识库如何处理过期/过时知识？

四步法：打标签 → 增量索引 → 时效感知 → 置信校准

  • 每个 Chunk 带 version 和 last_updated 标签，检索时过滤过期版本
  • 数据变更时只增量索引变化部分，不全量重建（成本低、延迟小）
  • 根据 query 判断时效性需求：政策类强依赖最新，通用知识容忍历史
  • 低置信度结果触发人工复核或规则兜底，不直接返回给用户
4
多路召回的原理是什么？RRF 融合怎么计算？

RRF（Reciprocal Rank Fusion）公式：

score(d) = Σ 1/(k + rank_i(d))，其中 k=60（平滑因子）

每路召回的同一文档，根据其在各路中的排名计算综合得分。三路（向量+BM25+关键词）取并集后 RRF 融合，可以兼顾语义相似性和关键词匹配。

5
上下文超限时有哪些裁剪策略？各有何优劣？
  • 硬截断：按 token 数量直接截断，最简单但可能切断关键信息，适合内容重要性均匀的场景
  • 软压缩（LLM MapReduce）：先用小模型对每个 Chunk 生成摘要，摘要总长超过限制时再对摘要合并压缩，保留关键实体和结论
  • 信息密度排序：计算每个 Chunk 的信息熵/密度，按密度排序后从高到低取满 token 额度，高密度块优先保留
  • MinerU 递归切片：用信息熵驱动，密度低的块继续细分，直到每块熵超过阈值，最适合复杂工业文档
