Evaluation：怎么判断大模型"真的好"？

一、为什么需要系统化评估

  • 能力量化：研发 / 选型 / 落地都需要"这个模型到底怎么样"
  • 横向比较：GPT-4 vs Claude vs Gemini vs Llama 谁更强？
  • 回归测试：SFT / DPO / LoRA 训练后是否真的提升？
  • 业务对齐：通用榜单 ≠ 业务场景，需要自定义评估集
  • 避免"看着好"：单 case 演示易骗人，统计指标才可靠
  • 评测陷阱多：数据污染、过拟合 benchmark、指标选择都会误导
核心认知：① 单一 benchmark 不可信，需多维度组合；② 通用榜单 ≠ 业务能力；③ 评测方法本身（prompt、few-shot、温度）会大幅影响结果；④ LLM-as-Judge 有偏，需用人类标注校准。

六、LLM-as-Judge（用大模型打分）

用强模型（GPT-4 / Claude 3.5）当裁判给候选模型打分，规模化、便宜、可复现。但有偏置。

两种范式

Single Answer：Judge(A_out) → 1-10 分

Pairwise：Judge(A_out, B_out) → "A 更好" / "B 更好" / "平局"

标准 prompt 模板（pairwise）

System: You are a fair judge of AI response quality.
[Question]
A: {response_A}
B: {response_B}
Output: {"winner": "A" | "B" | "tie", "reason": "..."}

常见偏置及解法

① 位置偏置（A 总是赢）→ 随机化 A/B 顺序，两次取平均

② 长度偏置（长答案赢）→ 加 length-instruction 提示

③ 自我偏置（GPT-4 偏 GPT-4 风格）→ 用第三方 judge 或 ensemble

④ 风格偏置（Markdown / Bullet 赢）→ 提示忽略格式

校准：用 500+ 人类标注样本计算 judge 与人类一致性，>80% 才可信。

八、评测陷阱（避坑指南）

陷阱 1：数据污染（Data Contamination）

Benchmark 题目被收进预训练 / SFT 训练集，模型"背答案"。解法：① 用 LiveCodeBench / MMLU-Pro / 动态更新 benchmark；② 检查 n-gram 重叠；③ 改写题目测试泛化。

陷阱 2：Judge 偏置（LLM-as-Judge Bias）

位置偏置（首选 A）、长度偏置、风格偏置、自我偏置（GPT-4 偏 GPT-4 风格）。解法：① 随机化 A/B；② 多次取平均；③ 用 ensemble（GPT-4 + Claude + Gemini）；④ 人类标注校准。

陷阱 3：单次采样 vs 多采样

Greedy 解（temperature=0）会低估真实能力。Self-Consistency 多采样投票可 +5-10%，但榜单是单次。生产中要明确：榜单分 = 实际分？

陷阱 4：CoT 触不触发

Math 评测需明确"是否允许 CoT"。zero-shot greedy vs zero-shot CoT vs 5-shot CoT 分数差 10-20pp。同一模型在 GSM8K：greedy 60% / CoT 80% / R1 风格 95%。

陷阱 5：超参数不一致

不同评测框架用不同 prompt、tokenizer、max length、温度，导致不可比。解法：① 用统一框架（lm-eval-harness / OpenCompass / HELM）；② 锁定 prompt 和超参；③ 注明评测配置。

陷阱 6：榜单过拟合

模型针对某个榜单微调（benchmark hacking）→ 真实能力没提升。解法：① 多个 benchmark 交叉；② 用业务数据集评估；③ 用 held-out 测试集。

陷阱 7：忽视分布偏移

Bench 分布 ≠ 真实分布。GSM8K 90% 不代表客服场景 90%。生产中必须用业务数据评估 + 持续监控。

陷阱 8：能力 vs 风格

LLM-as-Judge 常被"看起来专业"骗——Markdown 格式 / 长答案 / 自信口吻都加分。能力差的模型做"风格好"也能拿高分。解法：① IFEval 类可验证 benchmark；② 人类标注金标准。

十、业务落地：自定义评估集

  • 数据构造：从线上日志 / bad case 抽 500-5000 题，业务专家标注
  • 评估 prompt：和实际业务 prompt 一致，不要"评测 prompt 简化版"
  • 多维度：① 任务完成率（业务目标）② 事实准确率（幻觉）③ 风格（人设 / 品牌）④ 安全（合规 / 越狱）
  • 持续评估：每天 / 每周跑评测，跟踪回归
  • LLM-as-Judge 校准：500 题人类标注 + judge 一致性 > 80% 才放心用
  • 成本控制：评测用小模型（如 GPT-4o-mini）打分，大模型定期抽样
  • 报告：版本对比表 + 关键 bad case + 趋势图

十一、面试 FAQ

Q1：MMLU 是什么？怎么用？

A：Massive Multitask Language Understanding，57 学科 4 选 1 题目（10K+），测综合学科知识。0-shot / 5-shot 跑分。GPT-4 88%、Llama-3 70B 79%、Claude 3.5 89%。局限：① 多选易饱和；② 数据污染；③ 不测推理 / 工具调用。

Q2：HumanEval 为什么 90% 仍嫌低？

A：HumanEval 仅 164 题，且 2022 起已被数据污染（公开题目被收进训练集）。生产中要用 BigCodeBench / LiveCodeBench / SWE-bench（真实工程任务，GPT-4o 33%、Claude 3.5 49%）。Code 评测应看仓库级 + 动态更新。

Q3：Chatbot Arena 为什么是金标准？

A：真实人类用户盲测，Elo 评分系统统计意义强，避免 LLM-as-Judge 偏置。局限：① 样本偏分布（英语主导、英文用户偏好）；② 中文场景看国内榜单（CompassRank、SuperCLUE）。

Q4：LLM-as-Judge 有哪些偏置？

A：① 位置偏置（A 总是赢）→ 随机化顺序；② 长度偏置（长答案赢）→ 提示忽略长度；③ 自我偏置（GPT-4 偏 GPT-4 风格）→ 用第三方 judge；④ 风格偏置（Markdown 赢）→ 提示忽略格式。解法：ensemble + 人类标注校准。

Q5：CoT 触不触发影响多大？

A：GSM8K：greedy 60% / zero-shot CoT 80% / R1 风格 95%。同一模型分差 10-35pp。生产中必须明确：① 评测是否允许 CoT；② 业务用 CoT 还是单次；③ 榜单分 = 实际部署分？

Q6：怎么防止数据污染？

A：① 用动态更新 benchmark（LiveCodeBench / MMLU-Pro / 实时刷新的）；② 检查训练集与 benchmark n-gram 重叠（> 50% 视为污染）；③ 改写题目测试泛化（不变核心的同义改写）；④ 优先用 held-out 测试集（业务数据）。

Q7：业务模型怎么评估？

A：5 阶段流水线：① 离线 Bench（MMLU / IFEval）→ ② 内部 Eval（业务数据集 500+）→ ③ A/B（线上 1-5% 流量）→ ④ 监控（bad case / 用户反馈）→ ⑤ 反馈循环（bad case → 训练集）。关键：业务数据集 + LLM-Judge + 人类标注三者结合。

Q8：SWE-bench 为什么重要？

A：SWE-bench 测"修复 GitHub Issue"——真实仓库级 Python 代码工程任务，区分度高。GPT-4 33% / Claude 3.5 Sonnet 49% / R1 49%。比 HumanEval 难 10x，更能反映真实 Code Agent 能力。2024 后 Code 评测新标准。

Q9：MMLU-Pro / MMLU-Redux 和 MMLU 区别？

A：MMLU-Pro（2024）12K 题 + 10 选 1（不是 4 选），更难题 + 推理要求。Llama-3 70B 70% / GPT-4o 73% / Claude 3.5 78%。MMLU-Redux 是清洗版（去污染）。结论：MMLU 88% 已不算"高水平"，MMLU-Pro 80%+ 才是新基线。

Q10：为什么榜单分高但业务表现差？

A：① 分布偏移：bench 题目 ≠ 业务 query；② benchmark hacking：模型针对 bench 过拟合；③ 风格 ≠ 能力：LLM-Judge 被表面工程（Markdown / 长答案）骗；④ 任务复杂度低估：多步 / 工具调用 bench 难。解法：自定义业务评估集 + 真实 A/B + 用户反馈。

回答模板与加分项

30 秒电梯版

面试开场可以这样讲：大模型评估有 5 大类 benchmark：① 通用知识（MMLU / C-Eval）；② 数学推理（GSM8K / MATH / AIME）；③ 代码（HumanEval / LiveCodeBench / SWE-bench）；④ 人类偏好（MT-Bench / Chatbot Arena / IFEval）；⑤ Agent（AgentBench / GAIA / WebArena）。评测方法有 LLM-as-Judge、人类标注、A/B。常见陷阱：数据污染、Judge 偏置、超参不一致、榜单过拟合。生产中"5 阶段评估流水线"：离线 Bench → 内部 Eval → A/B → 监控 → 反馈循环。

5 分钟深入版

从动机（能力量化 / 横向比较 / 回归测试）→ 5 大类 Benchmark 全景 → 经典三件套（MMLU / GSM8K / HumanEval）→ Preference 类（MT-Bench / Arena）→ Code/Agent 评测（SWE-bench）→ LLM-as-Judge 与偏置 → 5 阶段评估流水线 → 8 大评测陷阱 → 主流框架（lm-eval-harness / OpenCompass）→ 业务落地。能讲清"为什么 HumanEval 90% 仍嫌低"、"Chatbot Arena 为什么金标准"、"为什么榜单分 ≠ 业务分"，立刻显得有真经验。

加分：知道评估局限

评估不是万能：① 数据污染（Bench 公开被收进训练集）；② Judge 偏置（LLM 评 LLM 有偏）；③ 能力 vs 风格（Markdown / 长答案 / 自信口吻骗分）；④ 分布偏移（Bench ≠ 业务）；⑤ 榜单过拟合（benchmark hacking）；⑥ 真实多步任务难（Agent / 工具调用 / 规划）。生产中必须"业务数据集 + LLM-Judge + 人类标注 + A/B"四件套。

加分：能讲一次工程踩坑

比如：自研客服模型 GPT-4-judge 打分 8.5/10，上线后用户满意度 60% → 查 LLM-Judge 与人类不一致，定位是 Judge 偏"长 Markdown" → 重写 prompt 加"忽略格式"、A/B 顺序随机化、用业务数据集 200 题人类标注校准 → Judge 与人类一致性 65% → 85%，满意度 60% → 82%。讲清"评测 → 调查 → 修偏置 → 校准 → 上线"五步，面试官会立刻认定你有真经验。
