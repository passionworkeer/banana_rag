PagedAttention：把 KV Cache 从"内存噩梦"变"虚拟内存"

vLLM 2023 提出。把操作系统虚拟内存的分页思想搬到 KV Cache：把每条请求的 KV Cache 切成固定大小的 block、用 block table 维护逻辑到物理的映射。效果：KV 显存碎片从 60-80% 降到 <4%，吞吐量提升 14-24x。本页讲清 block 机制、continuous batching、Prefix Sharing。

二、PagedAttention 核心机制

  • Block Size：每块固定装 N 个 token 的 KV（典型 N=16）
  • Block Table：每个请求一张表，记录"逻辑块 → 物理块"映射
  • 按需分配：请求增长时再申请新 block，零浪费
  • 逻辑连续、物理离散：attention 计算时按 block table 索引物理块
  • 显存池化：所有 block 来自统一物理池，无按请求预分配
类比 OS 虚拟内存：进程看到连续的地址空间，OS 用页表映射到物理页。PagedAttention 把"进程"换成"请求"，"页"换成"block"，"页表"换成"block table"。

三、Block Size 选择

小 block（4-8）→ 碎片少、调度灵活

大 block（32-64）→ 块表小、查找快

— — —

经验：N=16 是 sweet spot

vLLM 默认 block_size=16

过小：block table 项数爆（长序列 8K token 需 512 个 entry），调度开销大；过大：内部碎片（一个请求只用半块就占整个 block）。

五、Prefix Sharing（多请求共享前缀）

  • 场景：多用户问相同 system prompt（"你是 XX 客服..."）
  • 机制：相同前缀的 block 物理共享，不同请求的 block table 都指向同一组物理块
  • 写时复制：某请求要修改共享 block 时再分配新块（典型场景少）
  • 收益：system prompt 长（2K+）时显存节省显著

七、面试 FAQ

Q1：PagedAttention 灵感来自哪里？

A：操作系统的虚拟内存分页机制。OS 用页表把进程虚拟地址映射到物理页，进程看到连续地址但物理上分散。PagedAttention 把"进程"换成"请求"、"页"换成"block"、"页表"换成"block table"，解决 KV Cache 碎片。

Q2：block_size 怎么选？

A：经验 16（vLLM 默认）。权衡：太小 → block table 膨胀、调度开销；太大 → 内部碎片（一个请求占半块就浪费）。生产中可按业务调：短回答主导用 32、长生成主导用 8。

Q3：continuous batching 提升多少？

A：vLLM 论文报告 14-24x 吞吐量提升（vs HuggingFace Transformers 静态批处理）。生产实测：用户并发增加时提升更显著（QPS 随并发线性增长到 GPU 瓶颈）。

Q4：PagedAttention 适合所有模型吗？

A：目前主要支持 Decoder-only LLM（GPT / LLaMA / Qwen / Mistral）。Encoder-Decoder 模型的 cross-attention KV Cache 也支持（vLLM 0.4+）。MoE 模型需要额外处理专家路由 KV。

Q5：prefix sharing 在哪些场景收益最大？

A：长 system prompt 场景（客服 Agent 2K system prompt、RAG 检索 1K context、Agent 多工具描述）。多个并发请求共享同一前缀时，KV 显存可减半以上。

Q6：PagedAttention 的写时复制怎么实现？

A：block table 引用计数 + 写时分配。共享 block 引用计数 > 1；要写时引用计数 -1、新分配物理块、更新 block table。典型情况"读多写少"，性能影响可忽略。

Q7：PagedAttention 与 FlashAttention 关系？

A：正交。FlashAttention 优化 attention 计算本身（IO-aware）；PagedAttention 优化 KV Cache 显存管理。生产系统（如 vLLM）通常两者都开：FlashAttention 算得更快、PagedAttention 显存更省。

Q8：除了 vLLM 还有哪些实现？

A：vLLM（首创）、SGLang（更细的 RadixAttention）、TensorRT-LLM（NVIDIA 优化）、TGI（HuggingFace）、LMDeploy（商汤）。核心思想一致，工程优化各有侧重。

八、回答模板与加分项

30 秒电梯版

PagedAttention（vLLM 提出）把 OS 虚拟内存分页机制搬到 KV Cache：每条请求的 KV 切成固定大小 block、用 block table 维护逻辑到物理的映射。配合 continuous batching（任一请求完成立即塞新请求）实现 14-24x 吞吐量提升。碎片从 60-80% 降到 < 4%，还顺带原生支持 prefix sharing。

5 分钟深入版

从动机（KV Cache 碎片 60-80% 浪费显存）→ 类比 OS 虚拟内存 → block + block table 机制 → block_size 权衡（默认 16）→ continuous batching 提升 14-24x → prefix sharing 多请求共享前缀 → 写时复制实现 → 与 FlashAttention 正交。能讲清"为什么类比 OS 虚拟内存"、"为什么 block_size 默认 16"、"为什么 continuous batching 收益大"，立刻显得有真经验。

加分：踩坑案例

讲一次真实部署：① 用 HuggingFace Transformers 静态批处理，QPS 上不去；② 切 vLLM + PagedAttention 同样 GPU 跑 8x QPS；③ 但 block_size 设 4 调度开销爆炸，调到 16 才稳定；④ 长 system prompt 场景启用 prefix sharing，显存再省 30%。

加分：知道局限

PagedAttention 不是银弹：① block table 自身有开销（极小）；② 写时复制在生成多分支时可能浪费；③ 不直接优化 attention 计算（需配合 FlashAttention）；④ 仍受 GPU 显存总量限制。要诚实说"PagedAttention + FlashAttention + 量化 + Continuous Batching 是当前推理优化四件套"。
