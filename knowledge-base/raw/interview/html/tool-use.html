Tool Use 工具调用

Function Calling 原理、JSON Schema、多轮调用状态管理。

Function CallJSON SchemaMulti-turnErrorRetry

一、Function Calling 流程

  • 核心流程（6 步循环）：
    1. Tool 描述注入：把 tools（JSON Schema）作为 tools 字段传给模型
    2. 模型选 Tool：模型判断是否需要调工具，需要则输出 tool_calls（name + arguments）
    3. 客户端解析：解析 Function Call 输出，校验参数 schema
    4. 执行 Tool：客户端调用真实函数（HTTP / DB / 内部 API）
    5. 结果回灌：把 Tool 返回作为 role: tool 消息加入对话
    6. 继续生成：模型基于 tool 结果继续生成回答，可再次触发 tool call（多轮）
  • JSON Schema 关键字段：
    • name：工具名称（snake_case，全局唯一）
    • description：工具用途，模型判断调用的核心依据（写好描述 = 准确率 +30%）
    • parameters.type：固定 "object"
    • parameters.properties：参数列表 + 类型 + 描述
    • parameters.required：必填参数数组
    • strict（OpenAI）：是否严格模式（拒绝 schema 外字段）
  • 多轮调用：一个 prompt 多次 tool call
    • 并行多 Tool：模型一次输出多个 tool_calls，客户端并行执行
    • 串行多 Tool：先查后算（先 get_weather 再 send_msg）
    • 状态管理：messages 数组累积，每次 append role: tool 消息
  • 错误处理：
    • 参数校验失败：模型重新生成（带错误信息）
    • 工具不存在：返回 tool_call_id 对应的 error 消息
    • 超时：客户端设 timeout（默认 30s），失败时返回错误
    • 不可重试错误（4xx）：直接报错，让模型换工具
    • 可重试错误（5xx / 网络）：指数退避重试，最多 3 次
  • 重试策略：指数退避（1s → 2s → 4s）+ 最大次数（3 次）+ fallback（换工具 / 人工）
  • 安全：参数注入防护（白名单 / 长度限制 / 字符过滤）+ 工具白名单（只允许调注册过的）+ 审计日志

二、调用时序

Function Call 完整时序：用户问 → LLM 决定调工具 → 客户端执行 → 结果回灌 → LLM 生成回答。多轮调用时，重复 ②-⑤ 步骤，每次 append role: tool 消息。关键点：tool_call_id 关联（每个 call 对应一个 result）、消息累积（不能丢历史）、超时控制（防 hang 死）。

三、Tool Schema 示例

OpenAI Function Calling JSON Schema

{
  "type": "function",
  "function": {
    "name": "search_products",
    "description": "搜索蕉内商品，支持按关键词、品类、价格区间过滤",
    "strict": true,
    "parameters": {
      "type": "object",
      "properties": {
        "keyword": {
          "type": "string",
          "description": "搜索关键词，如"袜子"或"内衣""
        },
        "category": {
          "type": "string",
          "enum": ["袜子", "内衣", "家居服"],
          "description": "商品品类"
        },
        "price_min": {
          "type": "number",
          "description": "最低价格（元）",
          "minimum": 0
        },
        "price_max": {
          "type": "number",
          "description": "最高价格（元）",
          "maximum": 9999
        },
        "limit": {
          "type": "integer",
          "default": 10,
          "description": "返回商品数量",
          "minimum": 1,
          "maximum": 50
        }
      },
      "required": ["keyword"],
      "additionalProperties": false
    }
  }
}

关键设计：description 写清楚"做什么"（模型判断调用的核心），enum 限制可选值（避免模型自由发挥），required 明确必填（避免漏参数），additionalProperties: false（OpenAI strict 模式，拒绝额外字段）。

三、消息格式

Request（Client → Server）

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search_products",
    "arguments": { "keyword": "袜子" }
  }
}

Response（Server → Client）

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": { "items": [...] }
}

Error（参数缺失 / 工具不存在）

{
  "jsonrpc": "2.0",
  "id": 1,
  "error": { "code": -32602, "message": "keyword is required" }
}

Notification（Server 主动推送，无需回复）

{
  "jsonrpc": "2.0",
  "method": "notifications/resources/updated",
  "params": { "uri": "file:///orders/2026-06-03.json" }
}

五、面试 FAQ

Q1：Function Call 流程是怎样的？

A：6 步循环：① 把 tool 描述（JSON Schema）作为 tools 字段传给模型；② 模型判断要不要调，需要则输出 tool_calls（含 id、name、arguments）；③ 客户端解析并校验参数；④ 调真实函数；⑤ 把结果作为 role: tool 消息回灌；⑥ 模型基于结果继续生成，可再次调。OpenAI / Anthropic / Google 都支持，格式略有不同但思路一致。

Q2：JSON Schema 怎么写？

A：用 JSON Schema Draft 7 / 2020-12，定义 name（snake_case）、description（模型判断调用的核心，写清楚"做什么"和"何时用"）、parameters（type: object + properties + required）。高级：enum 限制可选值、minimum/maximum 限数值范围、pattern 限字符串格式、additionalProperties: false 拒绝额外字段。OpenAI 还支持 strict: true 严格模式。

Q3：多轮 Tool Call 怎么管理状态？

A：用 messages 数组累积。每次模型返回 tool_calls 后，客户端执行完每个工具，按 tool_call_id 顺序 append role: tool 消息，重新发给模型。OpenAI 还要求 assistant 消息也带 tool_calls 字段（保留模型原始输出）。注意：消息数组不能丢历史，否则 tool_call_id 关联会断。

Q4：Tool Call 错误怎么处理？

A：四类错误分类：① 参数错误（4xx 等价，模型重新生成）；② 工具不存在（return error message 给模型）；③ 执行失败（5xx / 超时，指数退避重试 1-3 次）；④ 不可重试（鉴权失败，fail fast）。重试策略：1s → 2s → 4s 指数退避 + jitter + 最多 3 次。fallback：换工具 / 跳过此步 / 兜底文案。

Q5：Tool Call 和 Prompt 注入风险？

A：Tool 结果回灌到 prompt 是注入面，恶意用户可通过工具返回值影响模型行为。防护：① 工具结果沙箱化（标记为 role: tool，不与 system prompt 混）；② 内容审查（关键词 / 长度限制 / 异常字符过滤）；③ 工具白名单（只允许调注册过的）；④ 危险操作要求人工确认（删库 / 转账）。Anthropic / OpenAI 在 SDK 层做了部分防护。

Q6：怎么调试 Tool Call？

A：四步调试。① 全链路 trace（用 LangSmith / Phoenix / 自建 trace_id）；② 记录每次 tool_call 的入参 / 出参 / 时延 / 错误码到 DB；③ 失败 case 单独标注（用 trace_id 关联）；④ 回放工具（mock LLM，固定输入看 Tool 执行）。生产中再加：调用埋点 + 异常告警 + 慢调用看板。

选型决策清单

选 Function Call 的场景

单次或少量 Tool 调用（1-3 步）、确定性强（知道要调什么）、用 OpenAI / Anthropic / Google API。生产首选，简单可控。

选 ReAct 的场景

动态多步决策（5+ 步可能）、环境不确定（每步要观察结果再决定）、需反思和重试。LangChain / AutoGen Agent 框架。需加循环检测。

选 Skill 的场景

固定工作流（code-review / 数据 ETL / PRD 生成）、需跨人复用、需版本管理和测试。Anthropic Skills / Cursor Skills 规范。

不引入工具调用的场景

纯文本任务（问答 / 总结 / 翻译）、无外部数据需求、不需执行动作。直接用 LLM 即可，引入工具反而增加复杂度和成本。
