Planner：让 Agent 从"想到哪做到哪"变成"先想后做"

Planner 是 Agent 系统的"项目经理"——把"完成用户目标"拆成可执行的步骤序列。主流范式 4 种：ReAct（边想边做）、Plan-and-Execute（先全部规划再执行）、ReWOO（Reasoning WithOUT Observation，规划与执行解耦）、LLMCompiler（并行执行）。本页讲清规划质量、失败回滚、Plan 评估。

一、4 种主流规划范式

二、规划质量的关键

  • 粒度：步骤不能太粗（"完成任务"）也不能太细（"点击按钮"）
  • 可执行：每步必须有清晰输入输出、能用工具 / 函数表达
  • 依赖关系：步骤间数据流正确（A 依赖 B 的输出）
  • 终止条件：明确何时算完成、什么情况下放弃
  • 回滚策略：步骤失败时如何恢复

三、Plan 评估指标

  • Plan 准确率：规划步骤是否合理（人工评估）
  • 完成率：按 plan 走到最后的比例
  • 步数利用率：完成任务的平均步数 vs 计划步数
  • 重规划次数：失败时需要 replan 几次
  • 总成本：规划 + 执行 + 重规划的总 token
"计划完美但执行差"和"计划粗糙但执行强"在生产中后者更常见——Planner 别过度设计，让执行有冗余。

四、ReWOO 代码示例

# ReWOO 三步
# Step 1: Planner 生成 plan
plan = """
Plan: 为了回答"特斯拉今年股价"需要：
Step 1: #E1 = Search["Tesla stock price 2024"]
Step 2: #E2 = Search["Tesla stock price 2023"]
Step 3: Answer = LLM["结合 #E1 和 #E2 总结变化"]
"""

# Step 2: Worker 收集 evidence
evidence = {
  "#E1": search("Tesla stock price 2024"),
  "#E2": search("Tesla stock price 2023")
}

# Step 3: Solver 填充变量、生成答案
filled = plan.replace("#E1", evidence["#E1"])
              .replace("#E2", evidence["#E2"])
answer = llm(filled)

ReWOO 核心思想：plan 阶段不调工具（省 token）、worker 阶段一次性收集所有 evidence、solver 阶段合并输出。适合检索密集型任务。

五、失败回滚 4 策略

  • 重试当前步：参数错误时重试，3 次后升级
  • 回退到上一步：用新信息重新规划
  • 全盘重规划：replan from scratch，复杂场景
  • 人工介入：超过 N 次重规划则升级

六、Subgoal 分解

把大目标拆成 2-5 个 subgoal，每个 subgoal 有独立完成判断。优势：

  • 每个 subgoal 可独立测试 / 评估
  • 失败定位快（哪个 subgoal 错一目了然）
  • 可并行（独立 subgoal 一起做）
  • 支持增量发布（先做核心 subgoal）
2-5 是经验 sweet spot：太少粒度粗，太多管理成本反而高。

七、面试 FAQ

Q1：ReAct vs Plan-and-Execute 怎么选？

A：任务短 / 工具多 / 反馈频繁 → ReAct（边走边纠）；任务长 / 步骤清晰 / 工具少 → Plan-and-Execute（先想后做）。ReAct 反应灵活但易跑偏；Plan-and-Execute 目标明确但 plan 错全错。

Q2：ReWOO 适合什么场景？

A：检索密集型任务（如"调研 X 公司"），需要并行查多个数据源。优点：plan 不调工具省 50% token，worker 一次性收齐 evidence。缺点：plan 错没救，所以对 planner 质量要求高。

Q3：LLMCompiler 和 ReWOO 区别？

A：LLMCompiler 把任务抽象成 DAG，无依赖任务并行执行、依赖任务串行。ReWOO 简单串行收集 evidence。LLMCompiler 实现复杂但并行加速显著。

Q4：Planner 错了怎么发现？

A：3 个信号：① 执行步数远超 plan（plan 不够细）；② 频繁回退 / replan（plan 整体方向错）；③ 下游工具返回"参数不合法"（plan 对工具能力理解错）。监控"完成率 / 平均步数 / replan 次数"三件套。

Q5：怎么让 Planner 输出更稳定？

A：4 个手段：① 强制 JSON schema 输出；② few-shot 给示例；③ 用 CoT 让 Planner 解释"为什么这么拆"；④ 校验每步输入输出格式（用 Pydantic）。

Q6：什么时候该 Replan？

A：3 个 trigger：① 步骤执行失败 N 次（如 3 次）；② 步骤返回"unexpected result"（说明 plan 假设错）；③ 上下文发生重大变化（用户改需求）。不要每步都 replan（成本爆炸）。

Q7：Planner 与 Router 关系？

A：Planner 决定"做什么"（任务分解），Router 决定"谁来做"（分配到哪个下游）。典型流程：Planner 出 plan → 每步交给 Router 选下游执行。两者常合并成一个 Agent（Plan + Route 一起做）。

Q8：Multi-Agent 系统中的 Planner 怎么设计？

A：常见模式"全局 Planner + 局部 Planner"：全局 Planner 拆子任务给子 Agent，每个子 Agent 内部有自己的局部 Planner 处理子任务。避免一个 Planner 管太多（易成瓶颈）。

八、回答模板与加分项

30 秒电梯版

Planner 是 Agent 的"项目经理"，把用户目标拆成可执行步骤。4 种主流范式：ReAct（边想边做）、Plan-and-Execute（先想后做）、ReWOO（规划/执行解耦省 token）、LLMCompiler（并行 DAG）。选择口诀：短任务 → ReAct，长任务 → Plan-and-Execute，检索密集 → ReWOO，延迟敏感 → LLMCompiler。失败时要 replan 但别每步都 replan。

5 分钟深入版

从动机（Agent 不会规划 = 想到哪做到哪）→ 4 种范式对比 → 规划质量 5 要素（粒度/可执行/依赖/终止/回滚）→ 评估指标 → ReWOO 代码示例 → 4 种回滚策略 → Subgoal 分解 2-5 sweet spot → Planner 与 Router 关系。能讲清"为什么 ReWOO 省 token"、"什么时候该 Replan"、"为什么 Plan-and-Execute 在长任务上更稳"，立刻显得有真经验。

加分：项目案例

讲一次"从 ReAct 切到 Plan-and-Execute"——比如数据分析 Agent 早期 ReAct 走 10+ 步仍找不到数据源，原因是没先想清楚"先查元数据还是直接查表"；切到 Plan-and-Execute 后先列"步骤 1 查元数据 → 步骤 2 选字段 → 步骤 3 跑 SQL"，3 步搞定，token 成本 -60%。

加分：知道局限

Planner 不是银弹：① Plan-and-Execute plan 错全错；② ReWOO 不能边走边纠；③ LLMCompiler 实现复杂；④ 多数场景 ReAct 已经够用。诚实说"Planner 选择取决于任务长度和反馈频率"得分更高。
