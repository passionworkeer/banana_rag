一、缓存的三层

  • 第一层：Prompt Cache（请求级 KV 复用）
    • 原理：相同前缀 prompt 的 KV 张量在请求间复用
    • 代表实现：Anthropic Prompt Caching（5min 缓存 + 1h 扩展）、OpenAI cached_tokens 字段、DeepSeek Context Cache
    • 节省：相同 1000 token system prompt，每次节省 ~80% 推理成本
  • 第二层：KV Cache 复用（会话级 / 推理优化）
    • 原理：同一会话的对话历史 KV 不重建，多轮对话 token 越多省得越多
    • 代表：vLLM prefix caching、SGLang RadixAttention、Hugging Face past_key_values
    • 节省：第二轮起每 token ~10x 加速（无 prompt 重新编码）
  • 第三层：语义缓存（应用级）
    • 原理：把请求 embedding 化，相似 query 直接复用历史回答
    • 代表：GPTCache、Redis + Embedding、LangChain SemanticCache
    • 节省：FAQ 类命中率 60%+，直接跳过大模型调用
  • 命中率优化：前缀稳定（system prompt 放最前 + 不要动态变化）、模板化（Few-shot 示例固定位置）、相似度阈值（cos > 0.95 才命中）
  • 失效策略：TTL（时间过期，默认 5min-1h）、版本号（prompt 升级时 bump version）、显式 invalidate（业务主动失效）
  • 适用场景：FAQ 客服、代码补全、模板化生成、文档总结、RAG 检索增强
  • 不适用场景：每次 prompt 完全不同、个性化对话（带用户历史）、长输出（生成 token 远超 prompt）

二、请求处理流程

请求先算 Cache Key（精确 hash 或 embedding），查 Redis / FAISS。命中直接返回历史回答；未命中调 LLM 后写回。监控命中率、P99 延迟、成本节省三件套是评估缓存效果的核心指标。

三、成本节省估算

$$\text{节省成本} = \text{命中率} \times \text{单次推理成本}$$

单层公式：命中率（Hit Rate）乘以单次推理成本。命中率 60% × 单次成本 0.01 元 = 每请求节省 0.006 元 / 1000 请求节省 6 元。

$$\text{综合成本} = (1 - \text{命中率}) \times \text{单次成本} + \text{缓存查询成本}$$

考虑缓存查询开销（Redis 0.5ms / Embedding 检索 5ms），命中率低于 10% 时缓存收益为负。FAQ 类场景（命中率 60%+）才值得上缓存。

$$\text{月节省} = \mathrm{QPS} \times 3600 \times 24 \times 30 \times \text{命中率} \times \text{单价}$$

实战算账：QPS 100、命中率 60%、单价 0.01 元/请求 = 月节省 100 × 86400 × 30 × 0.6 × 0.01 = 155 万元/月（理论值，实际看流量分布）。三层叠加效果最大。

$$\mathrm{P99} \,\text{改善} = (1 - \text{命中率}) \times \text{推理延迟} + \text{命中率} \times \text{缓存延迟}$$

延迟也类似加权。命中率 60% 时：P99 = 0.4 × 1200ms + 0.6 × 8ms = 485ms，比纯 LLM 推理的 1200ms 改善 60%。

KV Cache 原理

$$\mathrm{SelfAttn}(Q, K, V) = \mathrm{softmax}\!\left(\, \tfrac{Q \cdot K^{\top}}{\sqrt{d}} \,\right) \cdot V$$

自回归生成每步都算 Q·K·V，前面 token 的 K/V 张量可缓存复用，避免重算。这是 KV Cache 加速的核心。

$$\text{显存占用} = 2 \times n_{\text{layers}} \times n_{\text{heads}} \times \text{seq\_len} \times \text{head\_dim} \times \text{batch\_size}$$

7B 模型、32 层、32 头、head_dim 128、seq 2048、batch 1：~2 × 32 × 32 × 2048 × 128 × 2 bytes = 1GB。batch 32 直接 32GB，OOM 风险大。PagedAttention（SGLang / vLLM）按页分配缓解。

加速比 ≈ seq_len / 1（每 token 推理从 O(n²) 降到 O(1)）

128 token prompt + 256 token 生成：无缓存 384 × 384 = 147k 次注意力计算，有缓存仅新增 1 token O(1) 计算，加速 ~380 倍。

五、面试 FAQ

Q1：Prompt Cache 和 KV Cache 区别？

A：Prompt Cache 是请求级（API 厂商实现，跨请求复用 KV 张量，命中段不计费），KV Cache 是 token 级（推理引擎内部，维护当前序列的 K/V 张量避免重算）。前者是产品特性（Anthropic/OpenAI 卖的服务），后者是推理优化（vLLM/SGLang 必备）。两者可叠加。

Q2：语义缓存怎么判断相似？

A：双指标：① embedding 相似度（cos > 0.95 才算命中，余弦距离 < 0.05）；② 元数据匹配（用户身份 / 业务标签必须一致，避免"退货政策"在用户 A 和用户 B 答非所问）。常用 GPTCache 框架，支持多种距离度量和阈值配置。

Q3：命中率多少算合格？

A：分场景。FAQ 客服 60%+（问题重复度高）、电商咨询 30-50%（品类相似）、通用对话 20-30%（个性化高）、代码补全 40-60%（模板重复）。低于 10% 不值得上缓存（查询成本反而更高）。监控命中率 + 命中后用户满意度两个指标。

Q4：缓存失效怎么处理？

A：四种机制组合：① TTL 时间过期（最简单，5min-1h）；② 版本号（prompt 模板升级时 bump version，自动失效旧缓存）；③ 显式 invalidate（业务重要更新时主动调用 DEL）；④ 主动刷新（高一致性场景，定时重算）。生产中常 1+3 组合。

Q5：缓存会泄露隐私吗？

A：会。风险点：① 跨用户污染（用户 A 的回答给到 B）；② 缓存键含敏感字段（手机号、身份证）；③ 缓存被攻击拖库。防护：按用户隔离（key 加 user_id）、TTL 短（FAQ 1h / 通用 5min）、不缓存敏感字段、加密存储 + 访问审计。

Q6：怎么监控缓存效果？

A：四个核心指标。① 命中率（Hit Rate）= 命中次数 / 总请求数；② P99 延迟（命中 vs 未命中对比）；③ 成本节省 = 命中数 × 单价；④ 命中回答的准确率（用户反馈或抽样人工评）。Grafana 看板实时监控，命中率异常下降自动告警。

选型决策清单

只上 Prompt Cache 的场景

用 OpenAI / Anthropic API、system prompt 长（>500 token）、不能改推理引擎。零成本，命中率 30-50%，立刻省 30%+ 成本。首选方案。

加 KV Cache 复用的场景

自部署推理（vLLM / TGI）、多轮对话占比高、second-turn 延迟敏感。prefix caching 配置简单（vLLM 默认开），second-turn 延迟 -90%。

加语义缓存的场景

FAQ / 客服 / 模板化问答占比高（>30%）、能接受 0.95 相似度阈值、需显著降本。GPTCache 上线 1-2 天即见效，命中率优化 2-3 周达 60%+。

不上缓存的场景

个性化对话（用户历史相关）、长输出（生成 2000+ token）、每次 prompt 完全不同（创意写作）、数据强一致（金融 / 医疗决策）。强行上缓存反而引入错配风险。
