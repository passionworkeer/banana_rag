Tree of Thoughts：把推理从"链"扩成"树"

Yao 等 2023 提出。把 Chain-of-Thought 的线性推理扩展成树：每一步生成多个候选 thought → 用评估函数打分 → 保留 top-k → 继续展开。配合 BFS / DFS 搜索，ToT 在 Game of 24、24 点、创意写作等需要"探索 + 回溯"的任务上比 CoT 提升 2-5x。代价是 token 成本指数级增长。

三、评估函数 3 类

  • 规则评估：可验证任务（24 点、填字游戏、约束满足）
  • Self-Eval：LLM 自己打分（"这个推理看起来对吗？1-10"）
  • 外部模型：用强模型当裁判（GPT-4 评 GPT-3.5 推理）
  • 投票/多数决：self-consistency 风格的多数投票
Self-Eval 噪声大，但成本低；规则评估最稳但只能用于特定任务；外部模型最准但慢。ToT 论文中 Game of 24 用规则评估，创意写作用 self-eval。

五、ToT 适用场景

  • Game of 24：4 个数字凑 24，需要枚举和回溯
  • 数学证明：多步推导、尝试不同策略
  • 填字 / 数独：约束满足 + 探索
  • 代码生成：多方案尝试 + 测试驱动筛选
  • 创意写作：多主题探索、择优
  • 战略游戏：多步规划 + 评估位置

六、ToT 不适用场景

  • 简单 QA：直接答，搜索浪费
  • 长生成：token 成本爆炸
  • 实时场景：搜索耗时无法接受
  • 无评估函数的任务：没"对/错"信号时搜索失效
  • 主观创作：评估不稳定、剪枝靠运气
判断口诀：能写出"对/错"规则 + 任务有清晰中间状态 + 答案搜索空间 ≤ 1000 → 可考虑 ToT。否则上 CoT + ReAct 更经济。

七、面试 FAQ

Q1：ToT 相对 CoT 的本质提升在哪？

A：CoT 是"一次性链"——错了就错到底。ToT 把"下一步"扩成"多个下一步"，配合评估函数剪枝，能"试错+回溯"。在需要探索的任务（24 点、规划）上效果提升 2-5x，但成本 5-50x。trade-off 要算清。

Q2：ToT 评估函数怎么写？

A：3 类：① 规则（"答案是 24 吗"），适用于可验证任务；② Self-Eval（LLM 1-10 打分），成本低但噪声大；③ 外部模型（GPT-4 评），最准但慢。实践中规则+self-eval 组合最常见。

Q3：b 和 k 怎么选？

A：b=每层扩展状态数（典型 3-5），k=每个状态生成的 thought 数（典型 3-10）。b×k 决定每层 LLM 调用数。b=1 退化为 CoT；b=5, k=5 是 ToT 论文常用配置。生产中 b=3, k=5 平衡效果和成本。

Q4：ToT 怎么避免组合爆炸？

A：3 个手段：① 评估函数强剪枝（剪掉 V(s) < 阈值的分支）；② 深度限制（max_depth 5-10）；③ 早停（达到目标即返回）。还可以用 beam search 把 b 限制在常数。

Q5：ToT 与 MCTS 关系？

A：MCTS（蒙特卡洛树搜索）用 UCB 选择 + 模拟评估，更精细但实现复杂。ToT 是简化版：直接用 LLM 评估 + 固定 b。可视为 MCTS 的"LLM 时代简化"。

Q6：ToT 与 self-consistency 区别？

A：self-consistency 多次独立采样后投票，无中间评估；ToT 有显式评估 + 剪枝 + 回溯。self-consistency 适合开放式生成，ToT 适合结构化推理。两者正交可叠加。

Q7：ToT 的 token 成本怎么控？

A：① 用小模型做 thought generation、大模型做 evaluation（双模型架构）；② b 和 k 按难度动态调（简单任务 b=1、复杂 b=5）；③ 评估函数前置剪枝（先生成 1 个 thought，评分低就直接放弃整条分支）；④ 缓存公共前缀。

Q8：ToT 在生产中真用吗？

A：直接用 ToT 的少，但"思维树思想"广为借鉴：DeepSeek-R1 的 self-revision、o1 的"internal CoT"、AlphaCode 的多方案生成都借鉴了 ToT 的"多分支 + 评估 + 剪枝"思想。纯 ToT 框架在 24 点、规划类 demo 中常见。

八、回答模板与加分项

30 秒电梯版

Tree of Thoughts 把 CoT 的线性推理扩成树：每步生成多个候选 thought，评估函数打分，剪枝低分，保留 top-b 继续。配合 BFS / DFS 搜索和回溯机制，在需要探索+回溯的难题（24 点、数学证明、代码生成）上比 CoT 提升 2-5x。代价是 token 成本 5-50x 增长，需要规则 / self-eval 评估函数支撑。

5 分钟深入版

从动机（CoT 不支持回溯）→ ToT 4 步循环（生成 / 评估 / 搜索 / 终止）→ BFS vs DFS 选择 → 评估函数 3 类（规则 / self-eval / 外部模型）→ 与 CoT/ReAct/Reflexion 对比 → 适用场景（24 点、规划、创意）→ 不适用（简单 QA、长生成、实时）→ token 成本控制（双模型 / 动态 b / 缓存）。能讲清"为什么 ToT 评估函数比 thought generation 更重要"，立刻显得有真经验。

加分：项目案例

讲一次"为什么 CoT 失败而 ToT 成功"——比如推理规划场景下 CoT 一次走错就全错；上 ToT 后用规则评估函数（"是否满足约束"）剪枝，复杂规划任务完成率从 35% 升到 78%。再讲成本控制：b 从 5 降到 3 后成本 -40%，效果几乎不变。

加分：知道局限

ToT 不是银弹：① 成本 5-50x 增长；② 需要可评估函数；③ 评估函数不准时剪枝失效；④ 复杂任务上 b 太小不够。诚实说"ToT 在 24 点、规划、代码多方案生成上效果显著，开放问答不值得"得分更高。
