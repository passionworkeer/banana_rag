MCP 协议

Model Context Protocol — Agent 工具调用的标准化协议，让 LLM 通过统一 schema 调用外部工具。

MCPJSON-RPCToolResourcePrompt

一、MCP 是什么

  • MCP 是什么：Anthropic 2024 年提出的开放协议，标准化 LLM 与工具/数据源的通信
  • 三大原语：
    • Tool（可调用函数）
    • Resource（可读取数据）
    • Prompt（可复用提示模板）
  • 通信方式：
    • stdio（本地进程间通信）
    • SSE（服务器推送，远程长连接）
    • HTTP（远程短连接）
  • 与 Function Call 的关系：
    • MCP 是协议层（如何传输、如何发现、如何管理）
    • Function Call 是模型输出格式（模型如何表达"我要调用工具"）
    • 两者互补：MCP 客户端解析 Function Call 输出，按 MCP 协议调用 Server
原语方向典型用途类比
ToolClient → Server执行动作：搜索、下单、发消息RPC 远程函数
ResourceClient ← Server读取结构化数据：文件、订单、配置REST GET 资源
PromptClient → Server拉取可复用提示模板（带参数）Prompt 片段库

通信方式对比

传输部署形态延迟适用场景限制
stdio本地子进程最低（IPC）IDE 插件、CLI Agent、读写本地文件不能跨主机、需随 Client 启动
SSE远程长连接中（HTTP/1.1）流式日志、事件订阅、服务端主动推送需要保持连接、反向代理需配 keep-alive
HTTP远程短连接中（每次建连）云上工具服务、一次性查询、跨网络调用流式能力弱、需自己实现重试与幂等
选型经验：本地工具优先 stdio，远程工具看是否需要流式推送：是 → SSE，否则 → HTTP 即可。

二、MCP 架构

Host 持有 LLM 与对话状态；MCP Client 负责发现 Server、解析工具调用、按协议转发；Server 暴露 Tool/Resource/Prompt 三大原语。三层职责清晰，松耦合易扩展。

三、消息格式

Request（Client → Server）

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "search_products",
    "arguments": { "keyword": "袜子" }
  }
}

Response（Server → Client）

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": { "items": [...] }
}

Error（参数缺失 / 工具不存在）

{
  "jsonrpc": "2.0",
  "id": 1,
  "error": { "code": -32602, "message": "keyword is required" }
}

Notification（Server 主动推送，无需回复）

{
  "jsonrpc": "2.0",
  "method": "notifications/resources/updated",
  "params": { "uri": "file:///orders/2026-06-03.json" }
}

消息字段速查

字段必填说明
jsonrpc是固定为 "2.0"
idRequest / Response关联请求与响应；Notification 不可带
methodRequest / Notification如 tools/call、tools/list、resources/read
params视 method 而定方法参数，结构由 method 定义
result / error二选一成功带 result，失败带 error（含 code + message）

五、面试 FAQ

Q1：MCP 和 Function Call 区别？

A：MCP 是协议层，定义怎么发现、传输、管理工具；Function Call 是模型输出格式，定义模型怎么表达"我要调用哪个工具"。两者互补：MCP Server 注册工具，模型输出 Function Call，MCP Client 解析后调用。

Q2：为什么需要 MCP 协议？

A：解决工具碎片化：每个 Agent 框架（LangChain / AutoGen / CrewAI）都要重复实现工具调用，MCP 统一后工具一次开发多端复用，模型与工具解耦，生态可以共享。

Q3：MCP 通信有几种方式？

A：stdio（本地子进程，低延迟，IDE 场景首选）、SSE（远程长连接，适合流式推送与事件订阅）、HTTP（远程短连接，部署简单，适配云上服务）。

Q4：MCP Server 怎么发现和注册？

A：客户端启动时按配置加载 Server 列表（mcp.json / 配置文件 / 环境变量），每个 Server 启动后通过 tools/list、resources/list、prompts/list 三个端点暴露自己的能力，Client 聚合后注入 prompt。

Q5：MCP 工具调用错误怎么处理？

A：客户端解析 JSON-RPC 的 error 字段（code + message），按错误码分类处理：-32600（无效请求）/ -32601（方法不存在）/ -32602（参数错误）/ 自定义业务码（执行失败），可结合重试与降级策略。

Q6：MCP 和传统 API 调用的本质区别？

A：传统 API 是写死在代码里的硬调用，开发者决定何时调用；MCP 把工具描述（schema + 用途）注入到 prompt，让模型在推理时自己决定要不要调、传什么参数。控制权从"程序员"下放给"模型"。

Q7：MCP 工具 schema 里有哪些关键字段？

A：核心是 name、description（模型判断是否调用的依据）、inputSchema（JSON Schema 描述参数类型与必填）、annotations（只读/破坏性等提示）。description 写得好不好，直接决定模型调用准确率。

Q8：MCP 的权限和隔离怎么做？

A：常见做法是 Server 端基于 OAuth/API Key 做身份鉴权，Client 端在调用前对参数做白名单校验，对返回结果做脱敏。生产环境还会引入审计日志与限流，避免模型被注入攻击后无限调用敏感接口。

回答模板与加分项

30 秒电梯版

面试开场可以这样讲：MCP 是 Anthropic 提出的 Agent 工具调用协议，把"模型怎么表达"（Function Call）和"工具怎么被发现和调用"（协议层）解耦，让工具一次开发、在多个 Agent 里复用。我们团队用 MCP 把内部 API 包装成 Server，前端对话机器人直接对接。

5 分钟深入版

从协议动机 → 三大原语 → 通信方式 → 时序图 → 错误处理与权限，逐层展开。最后落到你们项目的 Server 列表、调用量、稳定性指标（成功率/P99）。有真实数据能立刻拉开差距。

加分：知道 MCP 的局限

MCP 不是银弹：长 prompt 会增加 token 成本、工具数量爆炸时模型选择会变差、跨厂商 schema 语义不一致。建议结合"工具路由器 / 路由器-执行器"分层或预先做 Rerank 缓解。

加分：能讲一次踩坑

比如：description 写得模糊导致模型反复错调；stdio 模式下 Server 进程崩了 Client 没感知；SSE 走 Nginx 没配 proxy_buffering off 推送卡住。讲一次具体排查过程，面试官会立刻认定你有真经验。

面试官可能怎么追问

追问方向示范追问建议回应思路
协议细节JSON-RPC 2.0 和 1.0 的关键差异？2.0 强制 jsonrpc 字段、支持 id 为 null（Notification）、错误码标准化。抓住"标准化"和"幂等关联"两点。
工程落地你们 Server 是 stdio 还是 HTTP？为什么？答本地调试 stdio，生产云上 HTTP；SSE 仅在需要流式推送时用。结合鉴权、限流、日志谈。
性能与成本工具多到几百个怎么办？引入工具路由器或 Rerank，按场景只把 Top-K 工具塞进 prompt，控制 token 成本。
安全与权限模型被注入误调敏感接口怎么办？危险操作要求人工确认 / 加 dryRun 参数；Server 端做权限校验 + 审计；Client 端做参数白名单。
生态对比MCP vs OpenAI Plugins / LangChain Tools？Plugins 是厂商私有，LangChain Tools 是框架绑定，MCP 是开放协议，跨模型、跨框架复用性最强。
最后提示：MCP 仍是相对新的协议，面试允许说"这块我了解协议规范但没在生产用过"，但要能讲清楚原理 + 给出假设场景的设计。诚实 + 思路清晰 > 假装熟练。
