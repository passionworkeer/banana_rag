# 05 工程基础

## 1. Go 协程、线程和 GMP 调度是什么关系？

核心回答：

> Go 协程比线程更轻量，GMP 是 Go runtime 的调度模型：G 是 goroutine，M 是真正的线程，P 是执行所需的上下文资源。Go runtime 通过把大量 G 映射到少量 M 上执行，实现高并发调度。

要点：

- G 很轻，创建和切换成本低。
- M 是操作系统线程。
- P 负责调度本地 runnable G。
- work stealing 提高调度效率。

## 2. 什么情况下会发生 goroutine 泄露？

核心回答：

> 当 goroutine 一直阻塞且没有退出条件时，就会发生泄露。常见原因是 channel 无人接收、select 没有退出分支、定时器未停止、请求取消后没有传递 context。

常见场景：

- 无缓冲 channel 发送没人收。
- for-select 永久等待。
- 背景任务没设退出信号。
- 忽略 context cancel。

## 3. Go 的内存模型、mcache、mspan、mheap 是什么？

核心回答：

> Go 的内存分配是分层缓存设计。mcache 是每个 P 的本地缓存，mspan 是一段连续内存管理单元，mheap 是全局堆管理。这样做是为了减少锁竞争、提高小对象分配效率。

分层：

- **mcache**：本地缓存，快。
- **mspan**：管理一组固定大小对象或大块内存。
- **mheap**：全局堆，负责向操作系统申请和回收更大内存块。

## 4. Go 为什么要分级分配？

核心回答：

> 因为小对象分配非常频繁，如果每次都去全局堆加锁会很慢。分级缓存可以让大多数小对象直接在本地快速分配，只有缓存不足时才向上层申请。

## 5. MySQL 事务和 MVCC 怎么理解？

核心回答：

> 事务保证一组操作要么都成功，要么都失败。MVCC 是通过多版本数据和 Read View，让读写尽量互不阻塞，从而提升并发读性能。

事务特性：

- 原子性
- 一致性
- 隔离性
- 持久性

MVCC 关键：

- 每行记录带版本信息。
- 读操作根据 Read View 决定能看到哪个版本。
- 提高快照读性能。

## 6. MySQL 索引、B+ 树、索引覆盖怎么理解？

核心回答：

> B+ 树适合做数据库索引，因为它层数低、范围查询好、叶子节点有序且便于扫描。索引覆盖是指查询所需字段都能从索引里拿到，不必回表。

要点：

- 主键索引通常是聚簇索引。
- 二级索引叶子存主键。
- 覆盖索引能减少回表成本。

## 7. 常见 SQL 操作的时间复杂度怎么理解？

核心回答：

> 不能只背一个固定复杂度，要看有没有命中索引、是否范围查询、数据量多大。单点主键查询通常接近 `O(logN)`，全表扫描是 `O(N)`，范围扫描则和区间长度有关。

## 8. Redis 常用数据结构和 pipeline / Lua 的作用是什么？

核心回答：

> Redis 常用结构包括 string、hash、list、set、zset。pipeline 用来减少网络往返，Lua 用来把多个命令打包成原子执行，特别适合高并发下的限流、扣库存和状态更新。

## 9. 为什么有时 Redis 是中心节点，有时是共享缓存？

核心回答：

> 这取决于架构。作为中心缓存时，它承担统一数据访问层；作为共享缓存时，它主要服务多个应用实例，减少数据库压力。重点是要控制一致性、热点和失效策略。

## 10. MQ 延迟、低优先级单分不出去怎么处理？

核心回答：

> 一般从消息堆积、消费速率、优先级队列、分区策略和重试机制入手。低优先级如果总是挤占队列，可以分开 topic、分开消费者组，或者在消费端做优先级调度。

## 11. 为什么 WebSocket 不用 HTTP？

核心回答：

> HTTP 更适合请求-响应，WebSocket 适合长连接双向通信。对于需要实时推送、流式输出或频繁交互的场景，WebSocket 的开销更小，体验更好。

## 12. 分片上传后怎么拼接大文件？

核心回答：

> 一般先给每个 chunk 编号并校验 hash，上传完成后服务端按顺序合并，再做完整性校验。关键是处理幂等、断点续传和重复上传。

## 13. 令牌桶算法怎么根据优先级让高优请求先拿令牌？

核心回答：

> 可以把不同优先级的请求放在不同队列里，给高优队列更高的取令牌权重，或者设置独立配额。核心是不要让低优请求一直占满令牌。

## 14. `NoClassDefFoundError` 一般怎么排查？

核心回答：

> 通常是编译时有类、运行时找不到类，或者类初始化失败。排查时看依赖是否被打进包、版本是否冲突、类加载路径是否正确。

## 15. vLLM、SGLang 这类推理框架的优势是什么？

核心回答：

> 它们主要优化 LLM 服务的吞吐、延迟和 KV Cache 管理。vLLM 的 PagedAttention 更像“虚拟内存”式管理，SGLang 则在编排、前缀缓存和执行效率上有自己的优化。

## 16. 高并发 Agent 系统里，召回和生成阶段怎么优化延迟？

核心回答：

> 召回阶段用缓存、索引优化和并行检索；生成阶段用更短上下文、更快模型、流式输出和减少无效工具调用。整个链路上尽量把串行步骤拆成并行步骤。

## 17. 大文件传输怎么优化？

核心回答：

> 用分片、断点续传、校验、合并和并发上传。上传时只传变更块，下载时支持范围请求，服务端要有幂等和重试机制。

## 18. 什么是健康检查、管理面和数据面？和 k8s 中节点状态有什么区别？

核心回答：

> 管理面负责调度和控制，数据面负责真正转发和处理流量，健康检查只是判断服务或节点是否可用的一种信号，不能完全等价于实际业务状态。

## 19. 为什么数据库有时不能直接替代 etcd？

核心回答：

> etcd 更适合做高一致性的配置和状态协调，数据库更适合做业务数据存储。两者的语义、延迟模型和使用场景不同，不能简单互换。

## 20. 为什么要做请求队列调度系统？

核心回答：

> 当请求并发、优先级和资源约束同时存在时，必须有调度层来控制吞吐和公平性。否则容易出现高优请求被淹没、资源打爆或局部服务雪崩。

## 21. 调用大模型 API 时，为什么用 asyncio 异步编程？

核心回答：

> 大模型 API 调用通常是 IO 密集型，主要耗时在网络等待。asyncio 可以让一个线程同时挂起多个请求等待结果，提高并发利用率，而不是每个请求都阻塞一个线程。

适合场景：

- 多个独立 API 并发调用。
- RAG 多路召回。
- Agent 多工具并行。

## 22. vLLM 为什么推理性能好？

核心回答：

> vLLM 的核心优势是 PagedAttention 和高效 batching。PagedAttention 把 KV Cache 像分页内存一样管理，减少显存碎片，提高 batch 利用率，从而提升吞吐。

关键点：

- KV Cache 分页管理。
- 支持 continuous batching。
- 减少显存浪费。
- 更适合多请求并发服务。

## 23. SGLang 相比 vLLM 的优势可以怎么说？

核心回答：

> SGLang 更强调结构化生成程序、前缀缓存和多阶段推理编排，适合复杂 Agent / 多轮生成链路。vLLM 更常被强调高吞吐推理服务和 PagedAttention。

面试表达：

> 如果只是高吞吐文本生成，我会优先想到 vLLM；如果是复杂 prompt program、工具调用或多阶段推理编排，SGLang 的表达能力和缓存机制会更有吸引力。

## 24. 怎么设计可配置并发的请求队列调度系统？

核心回答：

> 用一个队列接收任务，用 worker pool 控制最大并发，用配置动态调整 worker 数量或信号量容量，再结合优先级队列、超时和取消机制保证稳定性。

模块：

- 输入队列
- 并发控制器
- worker pool
- 优先级策略
- 超时取消
- 指标监控

## 25. 如何用策略动态调整并发数量？和 TCP 拥塞控制有什么类比？

核心回答：

> 可以根据延迟、错误率、队列长度和下游负载动态调整并发。类比 TCP，系统稳定时逐步增加并发，出现超时或错误时快速降低并发。

策略：

- 延迟低、错误少：缓慢增加。
- 延迟升高：停止增加。
- 错误率高：快速降低。
- 队列堆积：结合限流和降级。

## 26. 红黑树、B+ 树、搜索树、HNSW 分别适合什么？

核心回答：

> 红黑树适合内存里的有序集合，B+ 树适合磁盘数据库索引，普通搜索树是基础结构但可能退化，HNSW 适合高维向量近似最近邻搜索。

对比：

- 红黑树：平衡二叉搜索树，插入删除查询稳定。
- B+ 树：多叉、低高度、范围查询好。
- 搜索树：概念基础，未平衡时可能退化。
- HNSW：图索引，适合向量检索。

## 27. 灰度切流和在线双跑是什么？

核心回答：

> 灰度切流是把少量真实流量逐步切到新版本，观察指标后再扩大。在线双跑是新旧链路同时处理同一请求，但通常只让旧链路结果对用户生效，新链路用于对比评估。

## 28. 数据库一天产生多少数据、现在多少量级，怎么答？

核心回答：

> 如果没有精确数据，不要编。可以说“我当时掌握的是某个模块的量级”，并说明自己如何评估容量：日增量、峰值 QPS、表规模、索引大小、归档策略。

## 29. Redis Lua 里常用哪些命令？

核心回答：

> 常见是 `GET`、`SET`、`INCR`、`DECR`、`EXPIRE`、`ZADD`、`ZRANGE`、`ZREM`、`HGET`、`HSET`。Lua 的重点是把多步操作变成原子逻辑。

## 30. 为什么用 WebSocket，不用 HTTP 或 SSE？

核心回答：

> HTTP 适合一次请求一次响应，SSE 适合服务端单向推送，WebSocket 支持双向长连接。如果客户端也要频繁发控制消息或实时互动，WebSocket 更合适。

## 附录 A：工程基础详细知识点

### A1. Go GMP 调度更详细的讲法

```text
G：goroutine，用户态轻量任务
M：machine，操作系统线程
P：processor，调度上下文，持有本地运行队列
```

执行关系：

```text
G 必须绑定到 M 上运行，M 需要拿到 P 才能执行 Go 代码。
```

为什么快：

- goroutine 栈小，可以动态增长。
- 调度发生在用户态，切换成本低。
- P 有本地队列，减少全局锁。
- work stealing 平衡负载。

### A2. goroutine 泄露排查清单

常见泄露代码形态：

```go
go func() {
    ch <- value // 如果没人接收，会永久阻塞
}()
```

排查方式：

- 看 goroutine 数是否持续增长。
- pprof 查看阻塞位置。
- 检查 channel 是否有关闭路径。
- 所有后台任务都传 `context.Context`。

### A3. MySQL MVCC 详细机制

InnoDB 每行隐含信息：

- `trx_id`：最后修改该行的事务 ID。
- `roll_pointer`：指向 undo log。
- undo log：保存历史版本。
- Read View：判断当前事务能看到哪些版本。

面试表达：

> MVCC 不是复制整张表，而是通过 undo log 串起历史版本，再用 Read View 判断可见性。这样普通快照读不用阻塞写，提高并发性能。

### A4. B+ 树为什么适合数据库索引

原因：

- 多叉树高度低，磁盘 IO 次数少。
- 叶子节点有序，适合范围扫描。
- 非叶子节点只存索引，能放更多 key。
- 数据库查询常见范围查询，不只是单点查询。

对比红黑树：

- 红黑树适合内存。
- B+ 树适合磁盘页。

### A5. Redis Pipeline 和 Lua 的差别

| 机制 | 作用 | 是否原子 |
|------|------|----------|
| Pipeline | 减少网络往返 | 不保证整体原子 |
| Lua | 服务端执行脚本 | 单脚本原子 |

例子：

> 限流、扣库存、抢锁这类多命令强一致逻辑，更适合 Lua；批量查询更适合 Pipeline。

### A6. WebSocket、SSE、HTTP 对比

| 协议 | 方向 | 适合场景 |
|------|------|----------|
| HTTP | 请求-响应 | 普通接口 |
| SSE | 服务端到客户端单向流 | LLM 流式输出 |
| WebSocket | 双向长连接 | 实时互动、协作、控制消息 |

面试表达：

> 如果只是模型流式返回，SSE 就够；如果客户端还要频繁发控制消息，比如暂停、继续、调整参数，WebSocket 更合适。

### A7. vLLM 的 PagedAttention 细节

传统 KV Cache 容易产生显存碎片。PagedAttention 借鉴虚拟内存分页思想，把 KV Cache 分成 block 管理。

优势：

- 减少连续显存要求。
- 提高 batch 利用率。
- 支持 continuous batching。
- 对多请求并发更友好。

### A8. 高并发 Agent 延迟优化分层

```text
入口层：限流、排队、缓存
检索层：并行检索、向量索引调参、结果缓存
工具层：异步调用、超时、熔断
生成层：短上下文、流式输出、小模型路由
调度层：优先级队列、动态并发
```

### A9. 令牌桶优先级调度

可以把队列拆成：

```text
high_priority_queue
normal_queue
low_priority_queue
```

每次有令牌时优先服务高优队列，或按权重服务：

```text
high:normal:low = 5:3:1
```

注意：

- 不能让低优任务永远饿死。
- 可以给低优任务设置最低保障。

### A10. 大文件分片上传细节

完整流程：

```text
申请 upload_id
  -> 客户端按 chunk 上传
  -> 每片校验 hash
  -> 服务端记录上传状态
  -> 全部分片完成
  -> 合并
  -> 整体 hash 校验
  -> 标记完成
```

关键点：

- 分片编号。
- 幂等上传。
- 秒传。
- 断点续传。
- 合并失败回滚。
